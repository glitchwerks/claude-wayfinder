# v0.2 design — integration flow

## Status

- **Issue:** #37
- **Milestone:** v0.2
- **Decision:** Skill-primary, power-user-with-existing-router (brainstorm Approach 1)
- **Drafted:** 2026-05-14
- **Approval:** pending

---

## Context

v0.1 shipped claude-wayfinder as an evaluation surface: the `/dispatch` Skill runs the deterministic 7-decision matcher against bundled fixtures so consumers can inspect the decision logic, but it does not intercept real session traffic (see `skills/dispatch/SKILL.md:L1-L13`). The underlying architecture — scorer, decision ladder, catalog schema — is stable and documented in `docs/design/2026-04-30-deterministic-first-router-design-v5.md`.

Issue #37 captures the gap: a consumer who wants to use claude-wayfinder as their actual router has no documented, supported path to wire their own catalog and invoke the matcher from their router agent. Three option shapes (reference router agent, UserPromptSubmit hook, Skill with proactive triggers) were evaluated during a design brainstorm. Approach 1 — Skill-primary, deliberate invocation, no shipped router agent — was chosen for the power-user-with-existing-router audience that is the realistic early adopter. This spec records those settled decisions and defines the three deliverables that constitute v0.2.

The v5 architecture (`docs/design/2026-04-30-deterministic-first-router-design-v5.md § 3`) remains unchanged. v0.2 promotes the existing `build_catalog.py` CLI to a first-class module subcommand and documents the integration contract that was previously informal.

---

## Audience and scope

**Target consumer:** a power-user who already has a working router agent. They author their own router prompt, construct dispatch context themselves (file paths, tool mentions, agent mentions, command prefix), and want a stable, callable matcher plus a way to build a catalog from their own agents and skills. They do not want a shipped reference router agent they have to adopt whole, and they do not want an auto-firing hook that processes raw prompts.

**Explicit non-goals for v0.2:**

- No reference router agent shipped in the plugin — the consumer owns their router.
- No `UserPromptSubmit` hook for automatic dispatch-context extraction from raw prompts — **deferred to v0.3 pending real adoption signal.** The hook primitive is separable from NLP-based dispatch-context extraction; a structured-signal hook (raw prompt + regex-matched paths + slash-prefix, leaving enrichment to the router) is a legitimate v0.3 option. v0.2 defers it because (a) the power-user audience constructs context themselves so the hook adds no value for them, and (b) shipping a hook well requires telemetry on dispatch decision quality that v0.2 does not yet produce.
- No bundled standalone binary (#6 — deferred; Python prerequisite is the v0.2 assumption).
- No marketplace listing on the official Anthropic marketplace (no supported submission flow yet).

## Architecture

Three layers wire together cleanly:

```
Consumer's router agent
        |
        | constructs dispatch context (JSON)
        v
  /dispatch Skill  ──── detects catalog presence ────► demo mode (bundled fixtures)
        |                                               [no catalog configured]
        | real-catalog mode
        | ($DISPATCH_CATALOG_PATH set OR
        |  $DISPATCH_CATALOG_PATH absent + match.py exits [CATALOG ERROR])
        v
python -m claude_wayfinder.match  (stdin: dispatch context JSON)
        |
        | reads
        v
  dispatch-catalog.json  ◄── python -m claude_wayfinder catalog build
  (consumer's catalog)          (one-time + on refresh)
        |
        v
  decision JSON  (stdout)
        |
        v
Consumer's router agent acts on decision
```

The Python module (`python -m claude_wayfinder.match`) is the canonical entry point, unchanged from v0.1. The Skill is a thin wrapper that manages mode detection and surfaces the decision to the router. The catalog build subcommand promotes the existing `build_catalog.py` CLI to a first-class entry point — the implementation is a thin delegation, not a new CLI design.

## Deliverable 1 — Catalog generation surface

**The work is promotion, not redesign.** `build_catalog.py` already has a complete argparse CLI. v0.2's job is to wire `python -m claude_wayfinder catalog build` as a first-class subcommand that delegates to that existing `main()`, preserving the full parameter surface. This spec previously described a 3-flag wrapper; that framing was wrong and is corrected here.

### CLI surface — full parameter table

`python -m claude_wayfinder catalog build` exposes every parameter the underlying `build_catalog.py` CLI exposes. The table below is derived verbatim from `build_catalog.py:L1952-L2015`:

| Flag | Required | Default | Description |
|---|---|---|---|
| `--skills-dir` | **Required** | — | Directory containing skill `SKILL.md` files |
| `--agents-dir` | **Required** | — | Directory containing agent frontmatter `.md` files |
| `--out` | **Required*** | see note | Output path for `dispatch-catalog.json` |
| `--log` | **Required*** | see note | Output path for the catalog-generation log |
| `--plugin-overrides-dir` | Optional | `None` | Directory containing plugin-override trigger `.yml` files |
| `--plugins-dir` | Optional | `None` | Directory containing `installed_plugins.json` (Pass 2.5 plugin discovery) |
| `--builtin-agents-dir` | Optional | `None` | Directory containing builtin-agent sidecar `.yml` files (Pass 2.6 builtin discovery) |
| `--corpus` | Optional | `None` | Path to `routing-corpus.jsonl` for corpus-alignment scoring |
| `--project-root` | Optional | auto-detected | Path to the project git root for project-local overlay; when omitted, auto-detected via `git rev-parse --show-toplevel` |

**`--out` and `--log` defaults (implementation requirement):** The underlying `build_catalog.py:L1995-2004` marks both `--out` and `--log` as `required=True` with no default. The v0.2 subcommand wrapper **must** supply defaults so that the common invocation is not burdensome:

- `--out` defaults to `~/.claude/state/dispatch-catalog.json` — this is the path the Skill reads when `$DISPATCH_CATALOG_PATH` is unset.
- `--log` defaults to `~/.claude/state/catalog-build.log` — a sibling log adjacent to the catalog file.

When either flag is supplied explicitly, the default is ignored. This default-injection is an implementation responsibility of the v0.2 subcommand wrapper, not a change to `build_catalog.py` itself.

### Source-tagged precedence model — preserved exactly

`build_catalog.py`'s precedence semantics are preserved without change (see module docstring `build_catalog.py:L1-21`):

- Each catalog entry carries a `source` tag: `source="project"` for entries from `<root>/.claude/skills/**` and `<root>/.claude/agents/*.md`; `source="user"` for user-global entries from `--skills-dir` and `--agents-dir`.
- On name collision, `source="project"` overrides `source="user"`.
- Plugin overrides are applied from `--plugin-overrides-dir` at `~/.claude/triggers/<plugin>/<skill>.yml`.

The discovery model is: one `--skills-dir`, one `--agents-dir`, `--project-root` for project overlay, `--plugin-overrides-dir` for plugin override. There is no repeated-flag primitive — the source-tagged precedence model already encodes the layering that matters.

### Console-script entry points

`pyproject.toml`'s `[project.scripts]` table will declare:

- `claude-wayfinder = "claude_wayfinder.cli:main"` — the catalog build entry point (and entry point for any future subcommands)
- `claude-wayfinder-match = "claude_wayfinder.match:main"` — direct matcher invocation, equivalent to `python -m claude_wayfinder.match`

Both `python -m` invocation forms remain supported as equivalent invocations. The console scripts are the recommended form for Makefiles, CI jobs, and shell aliases. The integration guide must use console-script forms in all examples.

### Error handling

| Condition | Behavior |
|---|---|
| Source directory missing or unreadable | Warn to stderr, skip that source, continue building from remaining sources |
| Valid source directory is empty | Silently skip (zero entries contributed from that source) |
| Duplicate name across sources | Source-tagged precedence applies (`project > user`); emit a warning to stderr naming the winning and losing source |
| Output directory does not exist | Create it before writing; fail with a clear error if creation fails |

### Duplicate-name handling — open implementation question

Verify that `build_catalog.py`'s current collision behavior matches the `project > user` semantics described above before wiring the subcommand. If the current behavior differs, note the deviation in the implementation PR and align before shipping.

## Deliverable 2 — Skill behavior switch

The `/dispatch` Skill becomes mode-aware. The mode is implicit — detected by the presence of a catalog — not a flag the invoker passes.

### Section 2.1 — Mode detection decision table

**Key principle: demo mode is opt-in by absence of configured catalog — it is never a silent failure fallback.** Any real-catalog-mode failure is surfaced to the user. The Skill never silently routes against fixtures when the consumer intended real routing.

| `$DISPATCH_CATALOG_PATH` set? | Env path resolves (readable + valid JSON + valid schema)? | Outcome |
|---|---|---|
| Yes | Yes | **Real-catalog mode** — route against env-var path |
| Yes | No (missing, unreadable, or schema invalid) | **Hard error** — surface `[CATALOG ERROR]`; do NOT fall back to demo mode |
| No | n/a — env path not applicable | Continue to default-path check (rows below) |

| Default path (`~/.claude/state/dispatch-catalog.json`) present? | Default path catalog-loadable (readable + valid JSON + valid schema)? | Outcome |
|---|---|---|
| Yes | Yes | **Real-catalog mode** — route against default path |
| Yes | No | **Hard error** — surface the load failure; do NOT fall back to demo mode |
| No | n/a | **Demo mode** — bundled fixtures; emit a "no catalog configured — running in demo mode" banner in the Skill's output |

**Stale-mtime row:** When the resolved catalog's mtime is older than any source agent/skill file (and sources are enumerable), the Skill emits a warning to stderr — e.g., "Catalog mtime older than source files; consider running `claude-wayfinder catalog build`. Proceeding with stale catalog." — but **proceeds with the stale catalog**. Staleness is a degraded-quality signal, not an outright error.

The `[CATALOG ERROR]` surface behavior is already implemented in `match.py:L866-878` — the Skill must propagate that exit signal to the user rather than swallowing it.

### Section 2.2 — Real-catalog mode

When activated, the Skill expects the invoker (the consumer's router agent) to provide a composed dispatch context in the same JSON shape as v0.1's matcher input:

```json
{
  "task_description": "...",
  "file_paths": ["..."],
  "agent_mentions": ["..."],
  "tool_mentions": ["..."],
  "command_prefix": "..."
}
```

The Skill runs `python -m claude_wayfinder.match` with this context against the real catalog and returns the matcher's decision JSON verbatim. The consumer's router agent reads the decision JSON and acts on it.

### Section 2.3 — Demo mode

When no catalog is configured, the Skill runs against bundled fixtures. This is the current v0.1 behavior, unchanged. Demo mode preserves the evaluation-surface use case for new consumers inspecting the matcher for the first time.

### Section 2.4 — SKILL.md preamble requirements

The updated `skills/dispatch/SKILL.md` must include a clear preamble that:

1. Names both modes and states the activation condition for each.
2. States that the mode is implicit (presence of catalog), not a caller-supplied flag.
3. Describes the dispatch context JSON shape expected in real-catalog mode.
4. States that the consumer's router agent must include `Skill` in its `tools:` frontmatter for `/dispatch` to be invocable. Example of correct frontmatter: `tools: Glob, Grep, Read, Edit, Write, Bash, Skill, ToolSearch` — as used in `agents/code-writer.md` in the user's harness.
5. Points to `docs/integration.md` for the end-to-end wiring guide.

The `triggers:` block stays as `command_prefixes: [/dispatch]`. No proactive natural-language firing in v0.2 — the Skill is invoked deliberately by the consumer's router prompt. This was explicitly evaluated (option C in #37) and rejected to keep the integration contract intentional and auditable.

## Acceptance criteria

Derived from #37, adjusted for Approach 1's shape:

- [ ] **Catalog generation CLI is shipped and documented.** `python -m claude_wayfinder catalog build` (and `claude-wayfinder catalog build`) delegates to `build_catalog.py`'s full parameter surface, applying source-tagged precedence (`project > user`). `--out` and `--log` default to `~/.claude/state/dispatch-catalog.json` and `~/.claude/state/catalog-build.log` respectively when omitted. Warns on missing sources and name collisions.
- [ ] **Skill mode detection works end-to-end.** With `$DISPATCH_CATALOG_PATH` set to a valid catalog, `/dispatch` invokes the real matcher against the consumer's catalog and returns the decision JSON. Without a catalog configured, it runs demo mode with a clear banner. Any real-catalog-mode failure (missing file, invalid JSON, schema error) is surfaced as a hard error — no silent demo fallback.
- [ ] **Integration guide is published.** `docs/integration.md` contains all five sections defined in Deliverable 3 and is accurate against the shipped CLI and Skill behavior.
- [ ] **README install promise is updated.** The README no longer calls the plugin "evaluation surface only." It describes the v0.2 install as "router scaffold + matcher" and notes that the consumer's router agent must invoke `/dispatch` deliberately.
- [ ] **Graceful degradation is visible.** The mode-detection decision table in Section 2.1 is implemented exactly: hard error on real-catalog-path failures; demo mode only when no catalog is configured at all. Stale-catalog warnings are emitted to stderr without blocking routing.
- [ ] **CI coverage and manual verification.** Two halves: (a) *CI-covered* — subprocess tests on `python -m claude_wayfinder catalog build` (input → output catalog shape) and `python -m claude_wayfinder.match` (catalog + context → decision shape) verify the module contract; (b) *Out-of-band verification* — the Skill's mode-detection logic runs inside Claude Code's skill-invocation flow and is not reachable from pytest. Before v0.2 release, the implementer runs a **manual verification protocol** in a real Claude Code session: (1) clear all catalogs, invoke `/dispatch` — expect demo-mode banner; (2) set `$DISPATCH_CATALOG_PATH` to a valid file, invoke — expect real-catalog mode; (3) set env var to a missing file, invoke — expect hard error. Results are documented in `docs/integration.md` before release. The Skill behavior switch carries acknowledged **manual-verification risk**.
- [ ] **Console-script entry points declared.** `claude-wayfinder` and `claude-wayfinder-match` are declared in `pyproject.toml`'s `[project.scripts]` table; both resolve correctly after `pip install -e .` and execute identically to their `python -m` equivalents.

## Open implementation questions

The following were deferred from the brainstorm to the implementation PR. Each is one sentence.

- **Duplicate-name collision behavior in `build_catalog.py`** — the spec calls for `project > user` source-tagged precedence; verify `build_catalog.py`'s actual behavior before wiring the subcommand and align if it differs; deferred to implementation.
- **`--watch` mode for the catalog build CLI** — a file-system watch that rebuilds on change would reduce friction; explicitly out of scope for v0.2, punt to v0.3.
- **Decision logging to disk** — the Skill could optionally write each real-catalog decision to a corpus file for drift analysis; deferred; v0.2 ships decision JSON to the router only, no disk logging.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| **Catalog drift** — consumer's built catalog becomes stale after agents/skills change, causing the matcher to route against an outdated picture | Medium | `docs/integration.md` documents refresh triggers; the Skill warns when catalog mtime is older than any source file (see Section 2.1 stale-mtime row) |
| **Schema evolution** — the catalog schema is in active migration: v6 sidecar schema supersedes v5 inline-frontmatter (see `build_catalog.py:L11-14`); there is no `docs/schema.md` stable-contract document today. v0.2 consumers should expect a possible breaking change in v0.3 unless a versioned schema contract is added before v0.2 ships. **Option (a) — recommended:** document the schema as a versioned contract (`docs/schema.md`) in this same v0.2 milestone, so the risk table can say "schema stability is asserted by `docs/schema.md`." If that document is not produced before v0.2 ships, fall back to **option (b):** note explicitly in `docs/integration.md` that the catalog schema is mutable through v0.3, and that v0.3 migration tooling is a planned deliverable. | Medium | Produce `docs/schema.md` as part of v0.2 (option a), or set early-consumer expectations and commit to migration support as a v0.3 deliverable (option b) |
| **Performance on large agent/skill trees** — `build_catalog.py` scans every source file; consumers with hundreds of skills may see slow builds | Low | v0.2 targets single-user harnesses, not large teams; punt to v0.3 if it surfaces |
| **Early-consumer contract stability** — power-users who adopt v0.2 at launch will write router prompts against the dispatch context JSON shape; breaking that shape in v0.3 has real adoption cost | Medium | Document the dispatch context shape in `docs/integration.md` as a versioned contract; any change requires a migration note in the release |
