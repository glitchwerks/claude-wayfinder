## Context

v0.1 shipped claude-wayfinder as an evaluation surface: the `/dispatch` Skill runs the deterministic 7-decision matcher against bundled fixtures so consumers can inspect the decision logic, but it does not intercept real session traffic (see `skills/dispatch/SKILL.md:L1-L13`). The underlying architecture — scorer, decision ladder, catalog schema — is stable and documented in `docs/design/2026-04-30-deterministic-first-router-design-v5.md`.

Issue #37 captures the gap: a consumer who wants to use claude-wayfinder as their actual router has no documented, supported path to wire their own catalog and invoke the matcher from their router agent. Three option shapes (reference router agent, UserPromptSubmit hook, Skill with proactive triggers) were evaluated during a design brainstorm. Approach 1 — Skill-primary, deliberate invocation, no shipped router agent — was chosen for the power-user-with-existing-router audience that is the realistic early adopter. This spec records those settled decisions and defines the three deliverables that constitute v0.2.

The v5 architecture (`docs/design/2026-04-30-deterministic-first-router-design-v5.md § 3`) remains unchanged. v0.2 adds a supported multi-source catalog generation surface and documents the integration contract that was previously informal.

---

## Audience and scope

**Target consumer:** a power-user who already has a working router agent. They author their own router prompt, construct dispatch context themselves (file paths, tool mentions, agent mentions, command prefix), and want a stable, callable matcher plus a way to build a catalog from their own agents and skills. They do not want a shipped reference router agent they have to adopt whole, and they do not want an auto-firing hook that processes raw prompts.

**Explicit non-goals for v0.2:**

- No reference router agent shipped in the plugin — the consumer owns their router.
- No `UserPromptSubmit` hook for automatic dispatch-context extraction from raw prompts (rejected: the matcher performs better with a router-constructed context; hook-based extraction adds brittle NLP that detracts from the deterministic value proposition).
- No bundled standalone binary (#6 — deferred; Python prerequisite is the v0.2 assumption).
- No marketplace listing on the official Anthropic marketplace (no supported submission flow yet).
- No console-script CLI (`claude-wayfinder dispatch`, `claude-wayfinder catalog`) — surface area kept minimal for v0.2; the module entry point (`python -m`) is sufficient.

## Architecture

Three layers wire together cleanly:

```
Consumer's router agent
        |
        | constructs dispatch context (JSON)
        v
  /dispatch Skill  ──── detects catalog presence ────► demo mode (bundled fixtures)
        |                                               [no catalog configured]
        | real-catalog mode
        | ($DISPATCH_CATALOG_PATH set OR
        |  ~/.claude/state/dispatch-catalog.json exists)
        v
python -m claude_wayfinder.match  (stdin: dispatch context JSON)
        |
        | reads
        v
  dispatch-catalog.json  ◄── python -m claude_wayfinder catalog build
  (consumer's catalog)          (one-time + on refresh)
        |
        v
  decision JSON  (stdout)
        |
        v
Consumer's router agent acts on decision
```

The Python module (`python -m claude_wayfinder.match`) is the canonical entry point, unchanged from v0.1. The Skill is a thin wrapper that manages mode detection and surfaces the decision to the router. The catalog build command is a new CLI subcommand that wraps the existing `build_catalog.py` module.

## Deliverable 1 — Catalog generation surface

Expose catalog generation as a module entry point: `python -m claude_wayfinder catalog build`.

### CLI surface

```
python -m claude_wayfinder catalog build \
  --agents <dir> [--agents <dir> ...] \
  --skills <dir> [--skills <dir> ...] \
  --out <path>
```

`--agents` and `--skills` accept repeated values. This allows the consumer to compose a catalog from any combination of:

- User-scope: `~/.claude/agents`, `~/.claude/skills`
- Plugin-installed: `~/.claude/plugins/data/<plugin-name>/agents`, `~/.claude/plugins/data/<plugin-name>/skills`
- Project-local: `.claude/agents`, `.claude/skills`

The order of `--agents` and `--skills` arguments determines precedence when names collide across sources (see duplicate handling below).

`--out` defaults to `~/.claude/state/dispatch-catalog.json`. This matches the path already referenced in `skills/dispatch/SKILL.md` and the default used internally by `build_catalog.py` (line 9 of the module docstring). When `--out` is supplied explicitly, the default is ignored.

### Output schema

The output is the same JSON schema the matcher already consumes — whatever `build_catalog.py` produces today. This spec does not redesign the catalog schema; that is stable from v0.1.

### Error handling

| Condition | Behavior |
|---|---|
| Source directory missing or unreadable | Warn to stderr, skip that source, continue building from remaining sources |
| Valid source directory is empty | Silently skip (zero entries contributed from that source) |
| Duplicate name across sources | Last-write-wins by argument order; emit a warning to stderr naming the winning and losing source |
| Output directory does not exist | Create it before writing; fail with a clear error if creation fails |

The warn-and-skip policy on missing directories is intentional: power-users will frequently have one source absent on first run (e.g., no project-local agents yet). Hard failure on a missing source directory would make the command unusable during initial setup.

### Duplicate-name handling — open implementation question

The brief specifies last-write-wins by source order with a warning. Verify that `build_catalog.py`'s current behavior matches this before wiring the CLI subcommand. If the current behavior differs (e.g., first-write-wins, or error on duplicate), note the deviation in the implementation PR and align the behavior before shipping. See "Open implementation questions" below.

## Deliverable 2 — Skill behavior switch

The `/dispatch` Skill becomes mode-aware. The mode is implicit — detected by the presence of a catalog — not a flag the invoker passes.

### Mode detection

| Condition | Mode activated |
|---|---|
| `$DISPATCH_CATALOG_PATH` environment variable is set | Real-catalog mode, catalog at the specified path |
| `~/.claude/state/dispatch-catalog.json` exists | Real-catalog mode, catalog at the default path |
| Neither condition is met | Demo mode |

### Real-catalog mode

When activated, the Skill expects the invoker (the consumer's router agent) to provide a composed dispatch context in the same JSON shape as v0.1's matcher input:

```json
{
  "task_description": "...",
  "file_paths": ["..."],
  "agent_mentions": ["..."],
  "tool_mentions": ["..."],
  "command_prefix": "..."
}
```

The Skill runs `python -m claude_wayfinder.match` with this context against the real catalog and returns the matcher's decision JSON verbatim. The consumer's router agent reads the decision JSON and acts on it.

### Demo mode

When no catalog is configured, the Skill runs `python -m claude_wayfinder demo` against bundled fixtures. This is the current v0.1 behavior, unchanged. Demo mode preserves the evaluation-surface use case for new consumers inspecting the matcher for the first time.

### SKILL.md preamble requirements

The updated `skills/dispatch/SKILL.md` must include a clear preamble that:

1. Names both modes and states the activation condition for each.
2. States that the mode is implicit (presence of catalog), not a caller-supplied flag.
3. Describes the dispatch context JSON shape expected in real-catalog mode.
4. Points to `docs/integration.md` for the end-to-end wiring guide.

The `triggers:` block stays as `command_prefixes: [/dispatch]`. No proactive natural-language firing in v0.2 — the Skill is invoked deliberately by the consumer's router prompt. This was explicitly evaluated (option C in #37) and rejected to keep the integration contract intentional and auditable.

## Deliverable 3 — Integration guide (`docs/integration.md`)

A how-to guide for the power-user audience. This spec defines the required contents; the guide itself is authored in the implementation PR.

### Required sections and approximate length

| Section | Contents | Target length |
|---|---|---|
| **One-time catalog build** | Exact commands for three common compositions: (1) user-scope only, (2) user-scope + plugin, (3) user-scope + plugin + project-local. One command block per composition. | ~150 words |
| **Router-agent prompt snippet** | A copy-paste 20–40 line prose block for a router agent's body. Covers: (a) constructing dispatch context from the current turn, (b) invoking `/dispatch`, (c) reading the decision JSON, (d) acting on all seven decisions. The snippet is prompt prose, not Python — Claude Code router agents are text. | ~250 words |
| **Catalog refresh** | When to re-run catalog build: after adding/removing agents or skills; after upgrading the plugin. Three viable triggers: pre-commit hook, CI job, manual refresh. One paragraph per trigger. | ~100 words |
| **Drift telemetry pointer** | Brief note that v5's drift-feedback mechanism (advisory overrides, `self_handle_unaided` rates) is observable in the consumer's harness. Pointer to `docs/design/2026-04-30-deterministic-first-router-design-v5.md` for the full observability model. | ~50 words |

Total guide target: ~600 words. The guide is reference material, not a tutorial — favor precision over completeness.

## Acceptance criteria

Derived from #37, adjusted for Approach 1's shape:

- [ ] **Catalog generation CLI is shipped and documented.** `python -m claude_wayfinder catalog build` accepts `--agents` and `--skills` as repeated arguments, writes a valid catalog to `--out` (defaulting to `~/.claude/state/dispatch-catalog.json`), warns on missing sources, and warns on name collisions.
- [ ] **Skill mode detection works end-to-end.** With `$DISPATCH_CATALOG_PATH` set or the default catalog present, `/dispatch` invokes the real matcher against the consumer's catalog and returns the decision JSON. Without a catalog, it falls through to demo mode.
- [ ] **Integration guide is published.** `docs/integration.md` contains all four sections above and is accurate against the shipped CLI and Skill behavior.
- [ ] **README install promise is updated.** The README no longer calls the plugin "evaluation surface only." It describes the v0.2 install as "router scaffold + matcher" and notes that the consumer's router agent must invoke `/dispatch` deliberately.
- [ ] **Graceful degradation is visible.** A missing or unreadable catalog at the configured path produces a user-visible warning — not a silent fallback to demo mode. The distinction matters: demo mode against fixtures is not a degraded real-catalog run.
- [ ] **CI coverage without a full harness.** End-to-end behavior is tested via subprocess tests: invoke `python -m claude_wayfinder catalog build` with a synthetic agent/skill tree and assert the output catalog is well-formed; invoke `python -m claude_wayfinder.match` with the generated catalog and a sample dispatch context and assert the decision shape. SKILL.md format is covered by existing markdown lints. No Claude Code harness is required for these tests.

## Open implementation questions

The following were deferred from the brainstorm to the implementation PR. Each is one sentence.

- **Exact argument names for the catalog build CLI** — `--agents-dir` vs. `--agents`, `--skills-dir` vs. `--skills`: choose at implementation time, consistent with the existing `build_catalog.py` `--agents-dir`/`--skills-dir` flag names (see `build_catalog.py:L1952-L1963`); deferred to implementation.
- **Duplicate-name collision behavior in `build_catalog.py`** — the spec calls for last-write-wins by argument order; verify `build_catalog.py`'s actual behavior before wiring and align if it differs; deferred to implementation.
- **`--watch` mode for the catalog build CLI** — a file-system watch that rebuilds on change would reduce friction; explicitly out of scope for v0.2, punt to v0.3.
- **Decision logging to disk** — the Skill could optionally write each real-catalog decision to a corpus file for drift analysis; deferred; v0.2 ships decision JSON to the router only, no disk logging.
- **`$DISPATCH_CATALOG_PATH` override vs. `~/.claude/state/` default** — whether the env var should accept a directory (and discover the file) or must be a full file path: full file path is simpler; decide at implementation time.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| **Catalog drift** — consumer's built catalog becomes stale after agents/skills change, causing the matcher to route against an outdated picture | Medium | `docs/integration.md` documents refresh triggers; the Skill can warn if catalog mtime is older than any source file (implementation-time decision) |
| **Schema evolution** — if v0.3 needs to change the catalog schema, consumers who built catalogs under v0.2 will need to rebuild | Low | The catalog schema is already stable from v0.1; any v0.3 change must be backward-compatible or include a migration path |
| **Performance on large agent/skill trees** — `build_catalog.py` scans every source file; consumers with hundreds of skills may see slow builds | Low | v0.2 targets single-user harnesses, not large teams; punt to v0.3 if it surfaces |
| **Early-consumer contract stability** — power-users who adopt v0.2 at launch will write router prompts against the dispatch context JSON shape; breaking that shape in v0.3 has real adoption cost | Medium | Document the dispatch context shape in `docs/integration.md` as a versioned contract; any change requires a migration note in the release |
