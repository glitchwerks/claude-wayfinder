## Context

The v0.3.x patch chain (#67 → #77 → #82 → #87) traced one root cause — hook child processes cannot rely on the consumer's interactive shell PATH — through four failure modes. v0.3.5 (the latest released) ships sensible CLI defaults so bare `python -m claude_wayfinder catalog build` works when the consumer's `python` happens to have the package importable. The remaining gap: there is still **no guarantee** the consumer's `python` has the package, and the v0.3.4 `CLAUDE_WAYFINDER_PYTHON` env-var stopgap requires the consumer to opt in.

v0.4 closes the gap structurally: the plugin owns its own Python venv under `${CLAUDE_PLUGIN_DATA}`, materialized by a `SessionStart` hook, and every Python-spawning hook references the venv's Python by absolute path.

Anthropic plugin docs describe this pattern verbatim ([Plugins reference § Persistent data directory](https://code.claude.com/docs/en/plugins-reference#persistent-data-directory), fetched 2026-05-17):

> "A common use is installing language dependencies once and reusing them across sessions and plugin updates. Because the data directory outlives any single plugin version, a check for directory existence alone cannot detect when an update changes the plugin's dependency manifest. The recommended pattern compares the bundled manifest against a copy in the data directory and reinstalls when they differ."

The doc's worked example (the `node_modules` `diff -q` SessionStart) is the template this plan adapts to Python.

## Problem statement

Hook child processes have only these environment guarantees from the harness ([Plugins reference § Environment variables](https://code.claude.com/docs/en/plugins-reference#environment-variables), fetched 2026-05-17):

- `${CLAUDE_PLUGIN_ROOT}` — ephemeral; changes on every plugin update; do not write state here.
- `${CLAUDE_PLUGIN_DATA}` — persistent across plugin updates; resolves to `~/.claude/plugins/data/{id}/`.
- `${CLAUDE_PROJECT_DIR}` — current project root.

v0.4 must produce a design where the hook child process invokes a Python interpreter that has `claude_wayfinder` importable, using only those guarantees plus whatever is bundled in `${CLAUDE_PLUGIN_ROOT}`.

## Proposed design

### SessionStart contract (charges 1, 2, 6)

**Anthropic-documented behaviour** ([hooks](https://code.claude.com/docs/en/hooks), fetched 2026-05-17):

> "All matching hooks run in parallel, and identical handlers are deduplicated automatically."

and on exit-code 2 behaviour table:

> "SessionStart | No | Shows stderr to user only"

i.e. **SessionStart hooks run in parallel and cannot block the first prompt.** The doc additionally says SessionStart hooks "run on every session, so keep these hooks fast"; the default timeout is 600 seconds.

**Consequences for v0.4 design:**

- The plan's pass-1 phrase "ordered before `check-catalog-health.js`" was unfounded — no ordering is guaranteed. **Both `bootstrap-venv.js` and `check-catalog-health.js` must independently handle the "venv missing" state.** `check-catalog-health.js` currently only reads catalog state (no subprocess); it remains correct because it never invokes Python — see `hooks/check-catalog-health.js` (no Python spawn site exists today). It must not gain one in v0.4.
- A 30-60s bootstrap **does not freeze the UI**. The user can submit a prompt immediately. The first `UserPromptSubmit` (which fires `refresh-catalog-on-stale.js`) may race the bootstrap. The race is resolved by the refresh hook detecting `!fs.existsSync(venvPython)` and skipping silently (see § Hook invocation refactor). One-prompt latency on first install is the worst case; the catalog is stale-but-existing-from-prior-version on update.
- Bootstrap stderr is surfaced via `additionalContext` (per docs: "Claude Code wraps the string in a system reminder and inserts it into the conversation at the point where the hook fired"). 10,000-char cap applies; we truncate to 800 chars.

### `hooks.json` shape

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "node",
            "args": ["${CLAUDE_PLUGIN_ROOT}/hooks/bootstrap-venv.js"]
          },
          {
            "type": "command",
            "command": "node",
            "args": ["${CLAUDE_PLUGIN_ROOT}/hooks/check-catalog-health.js"]
          }
        ]
      }
    ]
  }
}
```

Note **exec form** — `command` is a bare program name, `args` is an array. Per docs ([Plugins reference § Environment variables](https://code.claude.com/docs/en/plugins-reference#environment-variables), fetched 2026-05-17):

> "In hook commands, use exec form with `args` so the path is passed as one argument with no quoting."

This converts every existing hook registration in `hooks/hooks.json:1-60` from shell-form to exec-form. The current shell-form registrations (`"command": "node \"${CLAUDE_PLUGIN_ROOT}/hooks/...js\""`) work because the path is double-quoted, but exec-form is the future-proof shape for paths containing spaces and is what the docs prescribe. **Sub-issue: convert all hook registrations to exec form** (sub-issue 2 below).

### Bootstrap pipeline

`hooks/bootstrap-venv.js` runs the following sequence:

1. **Read the bundled version** from `${CLAUDE_PLUGIN_ROOT}/pyproject.toml` (see § Version-of-truth resolution).
2. **Read the sentinel** at `${CLAUDE_PLUGIN_DATA}/venv.version` (JSON; see § Version sentinel schema). On parse error, treat as missing.
3. **Discriminate:**

   | State | sentinel | venv dir | venv-python exists | Action |
   |---|---|---|---|---|
   | Fresh | missing | missing | n/a | full bootstrap |
   | Version bump | exists, ≠ bundled | exists | n/a | tear down `venv/`, bootstrap |
   | Up to date | exists, == bundled | exists | yes | exit 0 silently |
   | Partial-bootstrap corruption | missing | exists | n/a | tear down, bootstrap |
   | Sentinel-only corruption | exists, == bundled | missing or no python | n/a | tear down (if dir present), bootstrap |
   | Cross-machine sync mismatch | exists | exists, wrong interpreter path | yes-but-broken | detected by import probe in step 7; tear down, bootstrap |

4. **Resolve a bootstrap interpreter** (see § Bootstrap interpreter source).
5. **Create the venv** via exec-form spawn: `spawnSync(bootstrapPy, ["-m", "venv", venvDir], { shell: false })`.
6. **Install the bundled wheel** (see § Package distribution choice): `spawnSync(venvPython, ["-m", "pip", "install", "--no-index", "--find-links", wheelDir, "claude-wayfinder"], { shell: false })`. Both `wheelDir` and `venvPython` are constructed via `path.join` from `${CLAUDE_PLUGIN_DATA}` / `${CLAUDE_PLUGIN_ROOT}` and passed as discrete argv elements — no shell quoting issues regardless of spaces in the consumer's home directory.
7. **Verify import:** `spawnSync(venvPython, ["-c", "import claude_wayfinder, sys; print(claude_wayfinder.__version__)"], { shell: false })`. Compare stdout to the bundled version; mismatch → fail like step 6.
8. **Write the sentinel** at `${CLAUDE_PLUGIN_DATA}/venv.version` (JSON).
9. **Exit 0** in all cases. Failures emit `additionalContext` banner; the harness shows it but does not block.

### Bootstrap interpreter source (charge 5)

Resolution order:

1. **`CLAUDE_WAYFINDER_BOOTSTRAP_PYTHON`** — namespaced env-var override. If set:
   - Probe with `spawnSync(value, ["-c", "import sys; sys.exit(0 if sys.version_info >= (3, 11) else 1)"], { shell: false, timeout: 5000 })`.
   - **On probe failure: fail loud.** Emit `[CATALOG BOOTSTRAP FAILED] CLAUDE_WAYFINDER_BOOTSTRAP_PYTHON=<value> failed Python ≥3.11 probe (exit=N, stderr=...). Override unset or fix the interpreter path.` Treat the override as a user assertion, not a hint — silent fallthrough would mask the consumer's misconfiguration and re-introduce the v0.3.3 "wrong interpreter" class of bug.
2. **Windows `py` launcher** (Windows only): try `py -3.13`, `py -3.12`, `py -3.11`, then `py -3`. Each candidate gets the same probe. First to succeed wins. Documented at <https://docs.python.org/3/using/windows.html#python-launcher-for-windows> (fetched 2026-05-17).
3. **POSIX `python3` then `python`**: try in order with the same probe. Skip Microsoft Store shim by treating any timeout, nonzero exit, or non-matching version as failure.
4. **Fail loudly** with the install hint and link to `https://www.python.org/downloads/`.

The renamed env-var (was `${PY}`) eliminates the collision with the Python launcher's `PY_PYTHON` family. The new name is symmetric with the existing `CLAUDE_WAYFINDER_PYTHON` (v0.3.4 stopgap in `hooks/refresh-catalog-on-stale.js:60-68`) — both follow the project's naming convention. The test seam stays `BOOTSTRAP_PYTHON_OVERRIDE` (test-only, never read in production code paths).

### Package distribution choice (charge 3) — REVISED

**Decision: bundle the pre-built wheel** (was option (a) in pass-1; previously rejected).

Pass-1 chose option (b) — install from `${CLAUDE_PLUGIN_ROOT}` source tree — and justified it on offline-friendliness grounds. Inquisitor correctly identified that PEP 517 build isolation pulls hatchling + transitive deps (pluggy, packaging, pathspec, trove-classifiers, editables) on every fresh bootstrap. Verified by reading `pyproject.toml:1-3`:

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

Bundling the wheel sidesteps the build-isolation problem entirely:

- Wheel artifact: `hooks/_python/claude_wayfinder-X.Y.Z-py3-none-any.whl` (the package is pure Python — single universal wheel).
- pyyaml is the sole runtime dependency. Two options for pyyaml:
  - **(a-1)** Bundle the pyyaml wheels alongside (Windows / macOS / Linux × cpython 3.11/3.12/3.13 = ~9 wheels, ~5 MB total). Install with `pip install --no-index --find-links "${CLAUDE_PLUGIN_ROOT}/hooks/_python" claude-wayfinder`. **Fully offline.** This is the decision.
  - **(a-2)** Bundle only the claude-wayfinder wheel; let pip fetch pyyaml from PyPI. Smaller artifact, but breaks offline. Rejected — re-introduces network dependency.

**Release tooling impact:** the existing release flow already builds a wheel via `python -m build`. A new step in the release workflow:

```
python -m build --wheel
pip download pyyaml -d hooks/_python --no-deps --platform <p> --python-version <v> --only-binary=:all:
# repeat for each (platform, python_version) pair
```

This is added to sub-issue 1.

### Hook invocation refactor — exec form mandate (charge 4)

Current shape (`hooks/refresh-catalog-on-stale.js:76`):

```js
const DEFAULT_GENERATOR_CMD = "python -m claude_wayfinder catalog build";
// ... downstream uses parseCmd (L281-289) to tokenize
```

New shape (exec form, no shell):

```js
const venvPython = process.platform === "win32"
  ? path.join(process.env.CLAUDE_PLUGIN_DATA, "venv", "Scripts", "python.exe")
  : path.join(process.env.CLAUDE_PLUGIN_DATA, "venv", "bin", "python");

const result = spawnSync(
  venvPython,
  ["-m", "claude_wayfinder", "catalog", "build"],
  { shell: false, encoding: "utf8", timeout: 30000 }
);
```

The args-array `spawnSync` pattern is identical to v0.3.4's fix in `hooks/refresh-catalog-on-stale.js:60-68`, just with `venvPython` instead of `CLAUDE_WAYFINDER_PYTHON || "python"`.

**Windows-path walkthrough.** When `${CLAUDE_PLUGIN_DATA}` is `C:\Users\First Last\.claude\plugins\data\claude-wayfinder-glitchwerks`:

1. `path.join` produces `C:\Users\First Last\.claude\plugins\data\claude-wayfinder-glitchwerks\venv\Scripts\python.exe` — a single string with the literal space preserved.
2. `spawnSync(venvPython, args, { shell: false })` passes that string as Win32 `CreateProcessW`'s `lpApplicationName` argument. Spaces are not interpreted; no tokenization.
3. The args array `["-m", "claude_wayfinder", "catalog", "build"]` is concatenated into `lpCommandLine` with each element quoted by Node's `child_process` implementation (Node ≥12 quotes any argv element containing spaces or tabs — see [Node docs § child_process.spawn](https://nodejs.org/api/child_process.html#child_processspawncommand-args-options), fetched 2026-05-17). Since these elements have no spaces, no quoting is added.
4. pip install (during bootstrap) similarly: `spawnSync(venvPython, ["-m", "pip", "install", "--no-index", "--find-links", wheelDir, "claude-wayfinder"], { shell: false })` — `wheelDir` is one argv element; even if it contains spaces, Node's quoting handles it for the Win32 child.

**Same shape for the bootstrap interpreter probe:** `spawnSync(candidate, ["-c", "import sys; sys.exit(...)"], { shell: false })`. The `-c` script is one argv element; semicolons and quotes inside it are not shell-interpreted because there is no shell.

**`DISPATCH_GENERATOR_CMD` test seam.** Currently `parseCmd` (L281-289 in `refresh-catalog-on-stale.js`) string-parses this env-var when set, used by `hooks/tests/refresh-catalog-on-stale.test.js` to inject `node fake_gen.js`. Sub-issue 3 keeps this seam working: when `DISPATCH_GENERATOR_CMD` is set, the hook uses the existing parseCmd path; when unset (production), the new exec-form `venvPython` path. This preserves all existing tests unchanged.

### Defensive behaviour when venv is missing

`refresh-catalog-on-stale.js` checks `!fs.existsSync(venvPython)`. If true:

- Log a one-liner: `[refresh-catalog] venv not yet materialized — skipping refresh (bootstrap may be in flight)`.
- Exit 0. The catalog from the previous version (or empty on first install) is used for this turn.
- Next SessionStart materializes the venv; subsequent turns work normally.

This handles charge 2's "first UserPromptSubmit races bootstrap" case explicitly.

### Cross-session invariants (charge 6)

**Invariants `bootstrap-venv.js` establishes:**

- `${CLAUDE_PLUGIN_DATA}/venv/{bin|Scripts}/python` exists and is a working CPython ≥3.11.
- `${CLAUDE_PLUGIN_DATA}/venv` has `claude_wayfinder` of the bundled version importable.
- `${CLAUDE_PLUGIN_DATA}/venv.version` is JSON describing the venv's identity.

**Support matrix:**

| Scenario | Survives? | Notes |
|---|---|---|
| (a) Cross-session, same project, same machine, no plugin update | Yes | All three invariants hold. Sentinel check passes; no rebuild. |
| (b) Cross-project, same machine, no plugin update | Yes | `${CLAUDE_PLUGIN_DATA}` is per-plugin, not per-project. The venv is project-agnostic — it just runs `claude_wayfinder catalog build` with project-detection logic in `refresh-catalog-on-stale.js`. **Note:** the catalog itself is `built_for_project`-tagged (`refresh-catalog-on-stale.js:224-231`); a project switch invalidates the catalog (forces a refresh on next prompt) but does **not** invalidate the venv. The two state files have different lifecycles by design. |
| (c) Cross-machine sync of `${CLAUDE_PLUGIN_DATA}` (roaming profile, OneDrive, Dropbox) | **Not supported.** | The venv encodes absolute paths to the bootstrap interpreter in its activation scripts and (more critically) in `pyvenv.cfg`'s `home =` field. A venv created on machine A pointing at `C:\Python311\python.exe` is broken when synced to machine B that has Python at a different path. **Detected** by the step-7 import probe — a broken venv fails the probe, triggers tear-down, and rebuilds on machine B. The user pays a one-time bootstrap cost per machine. **Explicit non-support.** A `README.md` troubleshooting note: "If you sync your `~/.claude` between machines, the plugin's Python venv will rebuild on each machine on first session. This is expected." |

The cross-machine handoff at the `refresh-catalog-on-stale.js` site: the hook computes `venvPython = path.join(process.env.CLAUDE_PLUGIN_DATA, "venv", ...)` fresh on every invocation. No path is stored anywhere between sessions. As long as `${CLAUDE_PLUGIN_DATA}` resolves to the right directory on the current machine (which the harness guarantees) and the venv at that path is intact, the refresh works. If the venv is sync-corrupted, `fs.existsSync(venvPython)` is the first line of defense (skip silently), and the next SessionStart's bootstrap-venv detects the import failure and rebuilds.

### Failure-mode discipline — partial-state path (charge 9)

Five failure surfaces (was three in pass-1):

1. **No bootstrap interpreter** — banner with install hint; exit 0.
2. **Override probe failed** — banner naming the failing override value; exit 0; **do not fall through**.
3. **`python -m venv` failed** — banner with truncated stderr; sentinel not written; venv directory may or may not exist. Cleanup: `fs.rmSync(venvDir, { recursive: true, force: true })` if it exists; failure of cleanup is logged but does not propagate (the next session's discriminator will detect partial state and re-cleanup).
4. **`pip install` failed mid-run** (the case pass-1 charge 9 flagged) — banner with truncated stderr. Cleanup sequence, in order:
   1. `fs.rmSync(sentinelPath, { force: true })` — remove sentinel first so the next session unambiguously discriminates "needs bootstrap".
   2. `fs.rmSync(venvDir, { recursive: true, force: true })` — tear down the half-built venv.
   3. If step 2 throws (Windows file lock from AV scanner mid-write is the realistic case), log a warning and exit 0. The next session sees `sentinel missing + venv dir exists` (the "Partial-bootstrap corruption" row in the discriminator table) and retries cleanup before bootstrap.

   **No retry loop.** Failure-of-cleanup logs and continues. The next-session retry path handles persistent failures.
5. **Import probe failed** — venv exists, `pip install` returned 0, but `import claude_wayfinder` fails (rare; usually means a corrupted wheel or interrupted install). Same cleanup as case 4.

All five exit 0. Banners are `additionalContext` strings; the 10,000-char cap mentioned in the docs is well above our 800-char stderr truncation.

### Update-time invalidation

Unchanged from pass-1. On plugin update, `${CLAUDE_PLUGIN_ROOT}` becomes the new cache directory; the bundled `pyproject.toml` has the new version; `${CLAUDE_PLUGIN_DATA}/venv.version` still has the old. Next SessionStart's discriminator fires "Version bump"; tear-down + rebuild; sentinel updated.

Mid-session update edge case (per docs: "When a plugin updates mid-session, hook commands… keep using the previous version's path. Run `/reload-plugins` to switch") works identically to pass-1's analysis.

### Version-of-truth resolution (charge 7)

**Source of truth: `pyproject.toml`.** Read in Node via a 10-line regex helper (`hooks/lib/pyproject-version.js`):

```js
// hooks/lib/pyproject-version.js
const fs = require("node:fs");
const path = require("node:path");

function readBundledVersion(pluginRoot) {
  const content = fs.readFileSync(path.join(pluginRoot, "pyproject.toml"), "utf8");
  // Find [project] section, then version = "..." within it
  const projectMatch = content.match(/^\[project\]\s*([\s\S]*?)(?=^\[|\Z)/m);
  if (!projectMatch) throw new Error("pyproject.toml: [project] section not found");
  const versionMatch = projectMatch[1].match(/^version\s*=\s*"([^"]+)"/m);
  if (!versionMatch) throw new Error("pyproject.toml: [project] version not found");
  return versionMatch[1];
}

module.exports = { readBundledVersion };
```

This eliminates `hooks/_python/VERSION` entirely. Three files become two (`pyproject.toml` + `.claude-plugin/plugin.json`), and the `plugin.json` version is the marketplace-facing string — these have different audiences and a lockstep tooling check is meaningful. Sub-issue 5 includes a `scripts/check-version-sync.py` that asserts `pyproject.toml [project] version == plugin.json version`; run in CI in the `lint` job and as a pre-tag check.

Node 22 ships `node:toml` but Node 20 does not; the regex avoids the dependency entirely and is unit-tested against the actual `pyproject.toml` fixture in `hooks/tests/pyproject-version.test.js`. Failure modes (malformed TOML, missing section) throw; the SessionStart hook catches and surfaces as banner.

### Version sentinel schema (charge 13)

`${CLAUDE_PLUGIN_DATA}/venv.version` is JSON:

```json
{
  "version": "0.4.0",
  "built_at": "2026-05-17T14:32:11Z",
  "interpreter": "C:\\Users\\chris\\AppData\\Local\\Programs\\Python\\Python311\\python.exe"
}
```

- `version`: the bundled `pyproject.toml` version the venv was built for. **The discriminator field.**
- `built_at`: ISO-8601 UTC timestamp of successful bootstrap. Debug only.
- `interpreter`: the bootstrap interpreter path. Debug only; useful for diagnosing cross-machine sync issues.

Schema versioning: there is no `schemaVersion` field in v0.4. If a v0.5 needs to add fields, JSON's structural flexibility handles it (unknown fields ignored). If a backward-incompatible change is needed, the sentinel-version mismatch path already handles "I don't recognize this sentinel" via the version compare — a v0.5 build would simply not match a v0.4 sentinel and rebuild.

## Test strategy (charge 11) — REVISED

### Unit-level (`hooks/tests/bootstrap-venv.test.js`)

Mock-seam tests cover the failure paths that real integration cannot easily exercise:

- `BOOTSTRAP_PYTHON_OVERRIDE` env-var injection (test seam, distinct from production `CLAUDE_WAYFINDER_BOOTSTRAP_PYTHON`).
- `BOOTSTRAP_SPAWN_OVERRIDE` env-var pointing at a JS file that the hook `require()`s in place of `child_process.spawnSync`. Tests inject fake spawn returns to simulate: venv creation success/failure, pip install success/failure, import probe success/failure, override probe failure.
- Discriminator table — one test per row.
- Failure-banner content — assert truncation, assert exit 0.

### Integration-level (`test-bootstrap-integration` CI job)

**De-path-filtered.** Runs on every PR and every release tag, regardless of which files changed. Pass-1's path filter was test theater that would let a `pyproject.toml` dependency bump skip the integration test — the exact failure shape that gave us v0.3.3.

Matrix: `ubuntu-latest`, `windows-latest` × Python 3.11, 3.12, 3.13 (via `actions/setup-python`).

Job steps:

1. `actions/checkout`.
2. `actions/setup-python` with the matrix version. (This also guarantees the `py` launcher is available on Windows — closes pass-1's `unverified` flag about CI runner Python availability.)
3. `python -m build --wheel` — build the claude-wayfinder wheel.
4. `pip download pyyaml -d hooks/_python --no-deps` — fetch the pyyaml wheel for the runner platform.
5. Set `CLAUDE_PLUGIN_DATA` and `CLAUDE_PLUGIN_ROOT` to temp directories; copy the plugin tree to `CLAUDE_PLUGIN_ROOT`.
6. `node hooks/bootstrap-venv.js < /dev/null` — run the bootstrap.
7. Assert: sentinel exists with correct JSON shape; `venv/{bin|Scripts}/python` exists; `<venv-python> -c "import claude_wayfinder"` exits 0; `<venv-python> -m claude_wayfinder catalog build --help` exits 0.
8. `node hooks/refresh-catalog-on-stale.js < <fake-prompt-json>` — verify the refresh hook spawns the venv-python correctly.
9. Re-run step 6 — verify no-op behaviour (sentinel matches, no rebuild).
10. Bump `pyproject.toml` version; re-run step 6 — verify rebuild path.

Approximate runtime: 60-90s per matrix cell, 6 cells = 6-9 minutes wall-clock with parallelism. Acceptable for a non-path-filtered job.

## CI implications (charge 8) — REVISED

Current CI matrix (`.github/workflows/ci.yml`): `lint`, `test-py311`, `test-py312`, `test-node`, `validate-manifest`.

v0.4 adds:

- **`test-bootstrap-integration`** — new job (see § Test strategy). Always runs.
- **`check-version-sync`** — runs in `lint`. Asserts `pyproject.toml [project] version == .claude-plugin/plugin.json version`. Closes the dual-truth issue from charge 7.
- **Invariant guard (replacing pass-1's substring grep)** — runs in `lint`. AST-based using `acorn` (the parser Node bundles internally via `acorn` as a transitive dep of many tools, or installed as a dev dep). Walks every `hooks/**/*.js` and inspects `CallExpression` nodes where callee is `spawnSync`, `spawn`, `exec`, or `execFile`. Asserts:
  - When the first argument is a string literal, it equals `"node"` OR `"git"` OR the result of `require("./lib/venv-path.js")`.
  - When the first argument is an identifier, the identifier's declared value (traced via scope analysis) resolves to a `path.join(...)` rooted at `process.env.CLAUDE_PLUGIN_DATA` OR is `process.env.CLAUDE_WAYFINDER_BOOTSTRAP_PYTHON` OR matches one of the bootstrap-candidate identifiers in `bootstrap-venv.js`.
  - **Invariant stated explicitly:** "No hook spawns a Python interpreter except through the venv-path resolver, the bootstrap interpreter resolver, or the documented `CLAUDE_WAYFINDER_BOOTSTRAP_PYTHON` override."

  Implementation note: the AST check is meaningful but limited — it cannot catch a hook that spawns `bash -c "python ..."`. For that residual gap, the invariant guard *also* asserts no hook's spawn-first-argument string literal contains `"bash"` or `"sh"` or `"cmd"` as the entire value, *unless* the file is a test-fixture under `hooks/tests/`. This is still imperfect (a hook could spawn `sh` indirectly), but the structural pattern of "spawn a shell to spawn Python" is loud enough at the AST level to flag.

  **If the AST check proves brittle in implementation:** drop it. Documented in sub-issue 4 as an explicit drop-decision option. Pass-1's correct point — "lint that doesn't catch the real failure mode is worse than nothing" — applies; we ship the check only if it actually constrains.

The existing `test-node` job picks up `hooks/tests/bootstrap-venv.test.js` automatically.

## Release shape (charge 10) — REVISED

Pass-1 proposed `v0.4.0-alpha.1 → v0.4.0`. Anthropic plugin docs are silent on whether `marketplace.json`'s `version` field accepts semver pre-release tags ([Plugin marketplaces § Version resolution](https://code.claude.com/docs/en/plugin-marketplaces#version-resolution-and-release-channels), fetched 2026-05-17 — quotes the field as "Plugin version" and gives examples like `"2.1.0"` but does not address prerelease syntax). The docs **do** explicitly describe a "release channels" pattern using separate marketplaces pointing at different git refs ([same page § Set up release channels](https://code.claude.com/docs/en/plugin-marketplaces#set-up-release-channels)).

**Revised strategy: release channels.**

- Maintain a separate `claude-wayfinder-prerelease` marketplace pointing at the `alpha` branch / ref of `glitchwerks/claude-wayfinder`.
- The main `claude-wayfinder` marketplace points at `main` and ships only tagged releases.
- A small testing pool installs from `claude-wayfinder-prerelease`; field-tests v0.4.x before main marketplace bumps.
- The `plugin.json` `version` field stays plain semver (`0.4.0`); the channel is the marketplace itself, not the version string. Per the docs:

  > "Each channel must resolve to a different version. If you use explicit versions, `plugin.json` must declare a different `version` at each pinned ref."

  We honor this by tagging prerelease commits with versions like `0.4.0-rc1` (in `pyproject.toml` and `plugin.json`) on the alpha branch only. Whether the docs accept the `-rc1` suffix in the version string is the open question — see § Pre-implementation verification checklist.

This is a documented, supported pattern rather than a guess about prerelease-tag handling.
