## Context

The v0.3.x patch series chased a single root cause through two distinct failure modes — both originating in the plugin hook child process trying to resolve Python tooling via the consumer's interactive shell PATH:

| Version | PR | Default generator command | Failure mode |
|---|---|---|---|
| v0.3.2 | [#67](https://github.com/glitchwerks/claude-wayfinder/pull/67) | `claude-wayfinder catalog build` | `spawnSync claude-wayfinder ENOENT` — the `[project.scripts]` shim is only on PATH inside the venv it was installed into. Tracked as [#76](https://github.com/glitchwerks/claude-wayfinder/issues/76). |
| v0.3.3 | [#77](https://github.com/glitchwerks/claude-wayfinder/pull/77) | `python -m claude_wayfinder catalog build` | `No module named claude_wayfinder` — bare `python` resolves to a different interpreter than the venv with the package, especially on Windows where `python.exe` from Microsoft Store / system install shadows venv Pythons. Tracked as [#80](https://github.com/glitchwerks/claude-wayfinder/issues/80). |

Both fixes share an unstated assumption: *the consumer's interactive shell environment is reachable from the hook child process*. That assumption is wrong. Hook processes inherit the environment of `claude` itself, which is launched from a desktop / IDE / terminal at potentially-arbitrary times and does not run inside any particular venv. The v0.3.3 in-source comment (`hooks/refresh-catalog-on-stale.js:42-57`) acknowledges this directly and names the v0.4 architectural change as the real fix.

Anthropic's plugin docs describe the canonical solution: `SessionStart` materializes a plugin-owned venv inside `${CLAUDE_PLUGIN_DATA}`, and subsequent hooks invoke `python` via the venv's absolute path. The docs include a worked example of this exact pattern for `node_modules` — see [Plugins reference § Persistent data directory](https://code.claude.com/docs/en/plugins-reference#persistent-data-directory) (fetched 2026-05-16).

Key facts from that page (fetched 2026-05-16) that this plan relies on:

- `${CLAUDE_PLUGIN_DATA}` is **"a persistent directory for plugin state that survives updates. Use this for installed dependencies such as `node_modules` or Python virtual environments"**. It resolves to `~/.claude/plugins/data/{id}/` where `{id}` is the plugin identifier with non-alphanumeric chars replaced by `-`.
- `${CLAUDE_PLUGIN_ROOT}` **"changes when the plugin updates"** — the previous version stays on disk ~7 days then is cleaned up. Treat as ephemeral; do not write state there.
- Update detection: Anthropic's documented pattern is **"compares the bundled manifest against a copy in the data directory and reinstalls when they differ"**, using `diff -q` as the discriminator. The doc's example: `diff -q "${CLAUDE_PLUGIN_ROOT}/package.json" "${CLAUDE_PLUGIN_DATA}/package.json" >/dev/null 2>&1 || (... install ...)`.
- Plugins are copied into `~/.claude/plugins/cache` per version; `${CLAUDE_PLUGIN_ROOT}` resolves into that cache directory, and **"installed plugins cannot reference files outside their directory"** (path traversal restriction). All bundled artifacts must live under the plugin root.

## Problem statement

The hook child process for `claude-wayfinder` must invoke a Python interpreter that has the `claude_wayfinder` package importable, **without** depending on:

- the consumer's interactive shell PATH,
- the consumer having activated any particular venv,
- the consumer having pip-installed `claude-wayfinder` into any particular interpreter,
- the consumer's OS-default `python` / `python3` / `py` shim resolving to anything in particular,
- any Python install path being stable between sessions.

The only environment guarantees a hook process has are: `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`, `${CLAUDE_PROJECT_DIR}`, whatever `claude` itself inherited. The plan must produce a design where the plugin owns its own Python runtime artifact and references it by absolute path under `${CLAUDE_PLUGIN_DATA}`.

## Proposed design

### SessionStart venv-materialization hook

Add a new hook `hooks/bootstrap-venv.js` registered on `SessionStart`, ordered **before** `check-catalog-health.js`. Responsibilities:

1. Read a version sentinel from `${CLAUDE_PLUGIN_DATA}/venv.version` (created by a previous successful bootstrap).
2. Read the bundled package version — either from `${CLAUDE_PLUGIN_ROOT}/pyproject.toml` (parsed inline; see option **(b)** below) or from a dedicated `${CLAUDE_PLUGIN_ROOT}/hooks/_python/VERSION` text file written by release tooling. Recommendation: the dedicated `VERSION` file, because parsing TOML in Node without deps is ugly and the build process can write the file deterministically.
3. If `venv.version` is missing **or** does not equal the bundled `VERSION`, run the bootstrap pipeline (see below) and on success write the new `venv.version`. On failure, delete `venv.version` so the next session retries (mirrors the Anthropic doc's `rm -f` recovery pattern).
4. If the versions match **and** `${CLAUDE_PLUGIN_DATA}/venv/Scripts/python.exe` (Windows) or `${CLAUDE_PLUGIN_DATA}/venv/bin/python` (POSIX) is present, exit 0 silently — no work needed.
5. Always exit 0 (never block session start). On bootstrap failure, emit a clearly-labeled `additionalContext` warning so the user sees what happened in the session log — see § Failure-mode discipline below.

**Bootstrap pipeline:**

1. Resolve a bootstrap interpreter (§ Bootstrap interpreter source).
2. `<bootstrap-python> -m venv "${CLAUDE_PLUGIN_DATA}/venv"`.
3. `"${CLAUDE_PLUGIN_DATA}/venv/{bin|Scripts}/python" -m pip install --upgrade pip` (one-shot, silent failure non-fatal — older pip works fine).
4. Install the bundled package — exact command depends on the distribution choice (§ Package distribution choice).
5. Verify import: `"${venv-python}" -c "import claude_wayfinder; print(claude_wayfinder.__version__)"` — abort and surface error if this fails.
6. Write `${CLAUDE_PLUGIN_DATA}/venv.version` with the bundled `VERSION` string.

#### Bootstrap interpreter source

This is the irreducible "you need *some* Python to make a venv" problem. Resolution order:

1. **`PY` environment variable** — if `${PY}` is set and points to a working Python ≥3.11, use it. Lets power users override.
2. **The Windows `py` launcher** (`py -3.11`, `py -3.12`, `py -3`) — present on virtually every Windows machine with any modern Python install. Try in that order; first to succeed wins. Documented at <https://docs.python.org/3/using/windows.html#python-launcher-for-windows> (fetched 2026-05-16).
3. **`python3` then `python`** on PATH — POSIX fallback; on Windows these often resolve to the Microsoft Store shim that immediately exits with a "Python was not found" message routed to stderr, so we must verify by actually running `<candidate> --version` and parsing output rather than just `which`-style probes.
4. **Fail loudly** — write the `[CATALOG BOOTSTRAP FAILED]` banner (§ Failure-mode discipline) with a one-line install hint: "no Python ≥3.11 found; please install from https://www.python.org/downloads/ and re-open Claude Code".

Each candidate is validated by running `<candidate> -c "import sys; sys.exit(0 if sys.version_info >= (3, 11) else 1)"` with a 5-second timeout. Anything that times out, errors, or returns nonzero is skipped.

`unverified:` whether the Microsoft Store Python shim exits 0 from `python --version` even when not installed — needs empirical check during implementation. If it does, the version-import probe above still catches it because the import fails.

#### Existence detection discriminator

`venv.version` text file in `${CLAUDE_PLUGIN_DATA}/`, containing the exact `VERSION` string the venv was built for. Discriminator logic:

| State | `venv.version` | `venv/` dir | Action |
|---|---|---|---|
| Fresh install | missing | missing | full bootstrap |
| Update with version bump | exists, ≠ bundled | exists | full rebuild (delete `venv/` then bootstrap) |
| Repeat session, same version | exists, == bundled | exists | no-op |
| Corrupted (partial bootstrap) | missing | exists | rebuild |
| Manual user deletion | exists | missing | rebuild |

Using a separate version file (rather than e.g. mtime comparison on `pyproject.toml`) means the discriminator survives the `${CLAUDE_PLUGIN_ROOT}` change on plugin updates — both old and new roots have a `VERSION` file at the same relative path; only the bundled string differs.

### Package distribution choice

The three options the brief named:

**(a) Bundle pre-built wheel** — `hooks/_python/claude_wayfinder-X.Y.Z-py3-none-any.whl`. Install with `pip install --no-index "${CLAUDE_PLUGIN_ROOT}/hooks/_python/<wheel>"`. Fully offline, deterministic, but requires release tooling to build the wheel and commit it; the wheel filename changes every version so release tooling must also delete the old wheel.

**(b) Bundle source tree + `pip install` from plugin root** — install with `pip install "${CLAUDE_PLUGIN_ROOT}"`. The current source already ships in the plugin tree (`src/claude_wayfinder/`, `pyproject.toml`). pip can build a wheel from the source tree on demand. The `[build-system]` already specifies `requires = ["hatchling"]` ([pyproject.toml:1-3](../../pyproject.toml)) so pip auto-installs hatchling into the build environment.

**(c) `pip install claude-wayfinder==X.Y.Z` from PyPI** — minimal bundled artifact, but requires network at install time and ties the plugin's behaviour to PyPI uptime. Also creates an awkward sequencing problem: a v0.4.0 plugin release must wait for the v0.4.0 PyPI release to land first, or the bootstrap fails for early upgraders.

**Recommendation: (b), bundle source tree, install from `${CLAUDE_PLUGIN_ROOT}`.**

Rationale:
- The source already lives in the plugin tree — no new artifacts to manage, no release-tooling expansion.
- Works fully offline (pip resolves `pyyaml` and `hatchling` from its own cache or falls back to PyPI only if not cached — and pyyaml is so ubiquitous it's almost always cached).
- No wheel-naming or wheel-staleness footgun.
- Avoids the chicken-and-egg sequencing of (c).
- The marginal install-time cost of building a tiny pure-Python wheel on first session is negligible vs. the simplicity win.

Tradeoff vs (a): (a) is faster on first install (~1-2s of wheel-build skipped) and fully reproducible offline. If install speed becomes a complaint, revisit. For v0.4 ship (b).

Tradeoff vs (c): (c) is the cleanest for "the package's only real artifact lives on PyPI" mental model. We can switch later if we want to remove the bundled `src/` from the plugin tree — but that's a separable change and not load-bearing for v0.4's actual goal (eliminating PATH-dependent invocation).

### Hook invocation refactor

Current shape (`hooks/refresh-catalog-on-stale.js:62`):

```js
const DEFAULT_GENERATOR_CMD = "python -m claude_wayfinder catalog build";
```

New shape — compute the venv Python's absolute path from `${CLAUDE_PLUGIN_DATA}`, which the harness exports to every hook subprocess per [Plugins reference § Environment variables](https://code.claude.com/docs/en/plugins-reference#environment-variables) (fetched 2026-05-16):

```js
const venvPython = process.platform === "win32"
  ? path.join(process.env.CLAUDE_PLUGIN_DATA, "venv", "Scripts", "python.exe")
  : path.join(process.env.CLAUDE_PLUGIN_DATA, "venv", "bin", "python");
const DEFAULT_GENERATOR_CMD = `"${venvPython}" -m claude_wayfinder catalog build`;
```

The `DISPATCH_GENERATOR_CMD` env-var override remains the test seam — unchanged.

**Defensive behaviour when the venv is missing:** if `${CLAUDE_PLUGIN_DATA}` is unset (tests, unusual harness), or `venvPython` does not exist on disk, the hook logs `[refresh-catalog] venv not materialized — skipping catalog refresh (bootstrap may have failed)` and exits 0. **Never blocks the prompt** — matches the existing fail-open contract.

**Audit pass:** any other Python-invoking hooks must be updated symmetrically. Recon shows `refresh-catalog-on-stale.js` is the only one today. As a guard against regression, add a unit test that grep-asserts no hook source contains a bare `"python "` or `"python3 "` string (excluding comments and the new resolution helper). Carry as a sub-issue.

**Shared helper:** factor the venv-Python-path computation into `hooks/lib/venv-path.js` so future hooks (and tests) share one resolver.

### Failure-mode discipline

Three failure surfaces:

1. **No bootstrap interpreter available** (no Python ≥3.11 on the system at all). Surface via `additionalContext` from the SessionStart hook:
   ```
   [CATALOG BOOTSTRAP FAILED] claude-wayfinder could not find a Python 3.11+
   interpreter to create its embedded venv. Install Python from
   https://www.python.org/downloads/ and re-open Claude Code. Catalog refresh
   will be skipped this session.
   ```
2. **Bootstrap interpreter found but `venv` / `pip install` failed.** Capture stderr from the failing subprocess; truncate to 800 chars; surface in `additionalContext`. Remove `venv.version` so next session retries. Surface as:
   ```
   [CATALOG BOOTSTRAP FAILED] venv creation or package install failed:
   <truncated stderr>
   The plugin will retry on next session start. Catalog refresh will be
   skipped this session.
   ```
3. **Bootstrap succeeded earlier but venv is gone / corrupted** (user deleted `~/.claude/plugins/data`, antivirus quarantined the venv, etc.). The `refresh-catalog-on-stale` hook detects `!fs.existsSync(venvPython)` and logs a short notice. Next SessionStart rebuilds.

All three exit 0. No hook ever blocks prompt submission or session start. This matches the existing v0.3.x contract — the failure modes get **louder** (banner with actionable text) but stay non-blocking. Equivalent to the existing `[CATALOG REFRESH FAILED]` shape in `refresh-catalog-on-stale.js`.

### Update-time invalidation

When the user runs `/plugin update claude-wayfinder`:

- `${CLAUDE_PLUGIN_ROOT}` changes to a new cache directory (per [Plugins reference § Environment variables](https://code.claude.com/docs/en/plugins-reference#environment-variables), fetched 2026-05-16: "This path changes when the plugin updates").
- `${CLAUDE_PLUGIN_DATA}` is **unchanged** (persists across versions).
- The bundled `hooks/_python/VERSION` file inside the new `${CLAUDE_PLUGIN_ROOT}` contains the new package version.
- `${CLAUDE_PLUGIN_DATA}/venv.version` still has the old version.

On the next SessionStart, the version mismatch fires, the old venv is deleted, the new bootstrap runs against the new bundled source, and the new `venv.version` is written. Single round-trip; no manual intervention.

**Mid-session update edge case:** per the docs ("When a plugin updates mid-session, hook commands… keep using the previous version's path. Run `/reload-plugins` to switch hooks…"), a mid-session update will keep firing the *old* `bootstrap-venv.js`, which writes the *old* `venv.version`. After `/reload-plugins` (or the next session), the new bootstrap sees a stale `venv.version` and rebuilds. This works correctly. The v0.4 design does not need to special-case mid-session updates.

## Test strategy

The current test infra (`hooks/tests/`) uses env-var injection to bypass real subprocesses (`DISPATCH_GENERATOR_CMD`, `SKILL_SIDECAR_PATH`, `CLAUDE_HOME`, `DISPATCH_CATALOG_PATH`). v0.4 introduces real `python -m venv` and `pip install` calls — slow, OS-dependent, network-touching. Apply the same injection-seam discipline:

### Unit-level (in `hooks/tests/bootstrap-venv.test.js`, new file)

Stub seams:
- `BOOTSTRAP_PYTHON_OVERRIDE` env var — if set, the hook uses it as the bootstrap interpreter without probing. Tests set it to `node` and verify the hook spawns it.
- `BOOTSTRAP_SPAWN_OVERRIDE` env var — if set, points to a JS file that the hook `require()`s in place of `child_process.spawnSync`. Tests inject fake spawn behaviour (return 0 / non-0, write stderr, etc.).
- `CLAUDE_PLUGIN_DATA` and `CLAUDE_PLUGIN_ROOT` — tests set to throwaway `os.tmpdir()` subdirs.

Test cases:
- Fresh install: no `venv.version`, no `venv/`. Hook spawns bootstrap pipeline. After fake-success, asserts `venv.version` matches bundled `VERSION`.
- Repeat session, same version. Asserts no subprocesses spawned.
- Update with version bump. Asserts old `venv/` deleted, bootstrap re-runs, new `venv.version` written.
- Corrupted state (`venv/` exists, `venv.version` missing). Asserts rebuild.
- No bootstrap interpreter available. Asserts `additionalContext` banner emitted, exit 0.
- `pip install` fails (fake spawn returns non-0 with stderr). Asserts banner with truncated stderr, `venv.version` removed.
- Hook exits 0 in all paths. Hardcoded assertion across every test.

For `refresh-catalog-on-stale.js`:
- New test: `CLAUDE_PLUGIN_DATA` set, venv-python path missing → hook logs skip notice, exits 0, does not call generator.
- Existing tests with `DISPATCH_GENERATOR_CMD` override continue to pass unchanged.

### Integration-level (CI gate, opt-in)

A new GitHub Actions job `test-bootstrap-integration` on `ubuntu-latest` and `windows-latest`:

1. Sets `CLAUDE_PLUGIN_DATA` and `CLAUDE_PLUGIN_ROOT` to temp dirs.
2. Copies the plugin tree into the fake `CLAUDE_PLUGIN_ROOT`.
3. Runs `node hooks/bootstrap-venv.js` with a real prompt JSON on stdin.
4. Asserts: `venv.version` exists, `venv/{bin|Scripts}/python` exists, `<venv-python> -c "import claude_wayfinder"` exits 0.
5. Runs `node hooks/refresh-catalog-on-stale.js` and asserts catalog generation works end-to-end.

This job runs on PRs touching `hooks/bootstrap-venv.js`, `hooks/refresh-catalog-on-stale.js`, or `src/claude_wayfinder/**`. Slower (~30-60s for venv + install) but high signal.

`unverified:` whether GitHub Actions runners on `windows-latest` ship the `py` launcher by default — needs verification at implementation time. If not, the CI job sets `PY=python` (or pre-installs Python via `actions/setup-python`).

## Release shape

**Recommendation: v0.4.0-alpha.1 → alpha.2 → … → v0.4.0 final.**

v0.3.x's patch-by-patch cadence worked because each patch was a one-line behavioural change. v0.4 is materially different: it adds a new hook, materializes a venv on consumer machines, and changes the interpreter-resolution model. Edge cases that don't appear in CI (Windows Defender quarantining `python.exe`, weird PATH on Linux distros that ship `python3.11` but not `python3`, IT-managed environments that block `pip install` from writing to user dirs) are likelier to surface only via real-consumer testing.

Proposed alpha process:

- **v0.4.0-alpha.1**: sub-issues 1-3 complete. Released to PyPI and the marketplace under a pre-release tag. Author + a small testing pool installs it; gathers feedback.
- **v0.4.0-alpha.2..N**: bug fixes from alpha-1 feedback. Each alpha bumps `plugin.json` and `pyproject.toml` versions in lockstep.
- **v0.4.0** final: when alpha series has been stable for ≥1 week with no new failure modes reported. Sub-issues 4-5 complete (lint guard + docs) gate the final release.

The epic body's process direction ("inquisitor adversarial review per the epic body's process") applies to the *plan* (this document) before sub-issue 2 starts implementation, not to each alpha — that's overkill. After plan approval, alphas can ship as PRs review-pass on the normal flow.

## Open questions / risks

1. **Microsoft Store Python shim on Windows** — when the user has not installed Python but has Windows 10/11, typing `python` opens the Store. Does invoking `python -c "..."` from a hook child process trigger the Store popup, return immediately with a Store-redirect exit, or hang? Needs empirical verification on a clean Windows install. Mitigation: the version-import probe in § Bootstrap interpreter source detects "not actually Python" and falls through.
2. **`pip install` writing to `${CLAUDE_PLUGIN_DATA}/venv`** — IT-managed Windows environments sometimes block `pip install` from writing outside specific directories. If `~/.claude/plugins/data/` is blocked, the bootstrap fails permanently. Mitigation: clear banner pointing the user to file an issue with their stderr; no auto-recovery possible without consumer intervention.
3. **Antivirus quarantine of newly-created `python.exe`** — copying the bootstrap interpreter into a venv creates a new `Scripts/python.exe` that some AV products scan and (rarely) quarantine. Detection: `venv/Scripts/python.exe` missing after a successful-looking `python -m venv` exit. Mitigation: rebuild on next session; document in README troubleshooting.
4. **Mid-session update timing** — documented in § Update-time invalidation. The design is correct but the user experience around `/reload-plugins` should be smoke-tested manually before v0.4.0 final.
5. **Bundled `src/` size impact on the marketplace cache** — the source tree is small (kilobytes) and pip's build output is cached in `${CLAUDE_PLUGIN_DATA}/venv/Lib/site-packages/`, not duplicated in the plugin cache. Risk negligible but worth checking with `claude plugin details` once shipped.
6. **`unverified:` `pyyaml` resolution offline** — if the consumer machine has *no* pip cache for `pyyaml` and *no* network, the bootstrap fails. pyyaml is the only runtime dependency ([pyproject.toml:20](../../pyproject.toml)), and it's pre-built wheel for Windows/macOS/Linux on every Python version. Realistic offline-install failures are very rare but possible; banner makes them diagnosable.
7. **Plan claim "v0.3.3 default fails on Windows because system `python` shadows venv"** — supported by [#80](https://github.com/glitchwerks/claude-wayfinder/issues/80) per recon, but I did not Read the issue body directly. Verify during sub-issue 2 implementation that #80's symptom matches the diagnosis in this plan's § Context table.
