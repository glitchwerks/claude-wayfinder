## Per-charge verification

### Charge 1 — SessionStart ordering

**Status: RESOLVED.**
**Verification basis:** hooks.md L441 — "All matching hooks run in parallel, and identical handlers are deduplicated automatically. Command hooks are deduplicated by command string and `args`." The revision drops the ordering assumption and requires both SessionStart hooks to handle "venv missing" independently. `check-catalog-health.js` is verified to have no Python spawn site today and the revision states it must not gain one.
**Residual risk:** none on this charge.

### Charge 2 — SessionStart blocking semantics

**Status: NEW-CONCERN-RAISED (the revision converted a defensible open question into a confidently-wrong claim).**
**Verification basis:** hooks.md L441 says hooks run in parallel **with each other** (intra-event), and L655 says exit code 2 on SessionStart "Shows stderr to user only" (no decision-control blocking). But L763-779 — the `additionalContext` injection section — states unambiguously that for SessionStart, `additionalContext` is delivered **"at the start of the conversation, before the first prompt."** No doc text I can find says the harness lets the first turn run before SessionStart completes; the architecture of "context injected before the first prompt" makes the opposite the natural interpretation.
**Residual risk:** the revision asserts (§ SessionStart contract, lines 71-72) that "SessionStart hooks run in parallel and cannot block the first prompt" — conflating "exit-2 cannot block" with "wall-clock cannot block." If the user submits a prompt 1s into a 60s bootstrap and the harness *does* gate the first turn on SessionStart completion (which the `additionalContext` timing strongly implies), the entire "first UserPromptSubmit races bootstrap" defensive architecture (the `!fs.existsSync(venvPython)` skip) is built around a race that does not happen — the prompt waits, and the user sees a 60s hang with no progress indicator. Conversely, if the harness does *not* gate the prompt, the bootstrap-failure banner is delivered *after* the user has already submitted and possibly received a reply, which is worse than a banner before. **This requires empirical verification — strace/observation against the real harness — not a doc-citation read of "parallel."** See charge 16 below.

### Charge 3 — Build isolation / offline claim

**Status: PARTIALLY-RESOLVED.**
**Verification basis:** the revision adopts wheel bundling. `pyproject.toml:1-3` confirms hatchling-with-PEP-517 is the build backend, so the choice to bundle correctly avoids the build-isolation pull. The revision's bundled artifact list ("Windows / macOS / Linux × cpython 3.11/3.12/3.13 = ~9 wheels") is the right shape.
**Residual risk:** the platform-tag enumeration is **incomplete and undocumented**. PyYAML on PyPI ships at least: `manylinux2014_x86_64`, `manylinux2014_aarch64`, `musllinux_1_1_x86_64` (Alpine), `musllinux_1_1_aarch64`, `macosx_*_x86_64`, `macosx_*_arm64`, `win_amd64`, and (recently) `win_arm64` — for each of 3.11/3.12/3.13, that is **24+ wheels, not 9**. The revision's `pip download pyyaml --platform <p> --python-version <v>` loop does not enumerate these explicitly. If a consumer is on Alpine Linux (Docker is the common case), the bundled `manylinux2014` wheel will fail to install with `ERROR: pyyaml-...whl is not a supported wheel on this platform`, and `--no-index` blocks the fallback. The "fully offline" claim survives only if the matrix is exhaustive *or* the bootstrap falls back to a source build with hatchling pre-staged — neither is in the revision. § Pre-implementation verification checklist item 6 hand-waves this with "fall back to source-build for that cell (with hatchling pre-installed in the bootstrap interpreter via `--no-build-isolation`)" — but the bootstrap interpreter is the *consumer's* interpreter, not a CI interpreter, and the revision provides no mechanism to stage hatchling into it offline. The offline claim still has a hole.

### Charge 4 — Windows path quoting / exec form

**Status: RESOLVED.**
**Verification basis:** plugins-reference.md L549 confirms the exec-form recommendation; hooks.md L320-329 walks through exec-form semantics including the Windows `.cmd`/`.bat` shim caveat (which does not bite us — we are spawning `node.exe` and `python.exe`, both real binaries). The revision's Windows-path walkthrough (§ Hook invocation refactor, lines 197-204) traces argv through `path.join` → `CreateProcessW` correctly. Node's `child_process.spawn` argv-quoting on Win32 is well-documented behavior.
**Residual risk:** none. The exec-form mandate is correct and the conversion of `hooks.json` to exec form is sub-issue 2 deliverable.

### Charge 5 — `${PY}` collision

**Status: RESOLVED.**
**Verification basis:** the revision renames to `CLAUDE_WAYFINDER_BOOTSTRAP_PYTHON`, matches the existing `CLAUDE_WAYFINDER_PYTHON` naming (verified in `hooks/refresh-catalog-on-stale.js:61-68`), and explicitly states fail-loud on probe failure rather than silent fallthrough.
**Residual risk:** none. The fail-loud-on-override choice is correct and called out explicitly (line 136).

### Charge 6 — Cross-session/project invariants

**Status: RESOLVED.**

The README troubleshooting note is the right user-facing answer.
**Residual risk:** none on this charge.

### Charge 7 — Three-file version truth

**Status: RESOLVED.**
**Verification basis:** the revision eliminates `hooks/_python/VERSION` and reads `pyproject.toml` via regex in `hooks/lib/pyproject-version.js`. The 10-line regex is presented inline and is correct for the actual `pyproject.toml:5-7` shape. ### Charge 8 — AST lint guard

**Status: PARTIALLY-RESOLVED.**
**Verification basis:** the revision replaces the substring grep with an AST-level check using `acorn`. **However:** `package.json` (read at HEAD) declares no `acorn` dependency, and the parenthetical "acorn (Node-bundled-equivalent)" is **incorrect** — Node's internal use of acorn is not exposed to user code as a public API. A consumer running `node hooks/check-no-bare-python-spawn.js` does not get `require("acorn")` for free; the project must add it to `package.json` as a dev dep and `npm install` it in the lint CI job. The revision's CI job (`.github/workflows/ci.yml` `test-node` runs on Node 20) does not currently `npm install` anything before running tests — it just runs `node --test hooks/tests/*.test.js`. The lint job runs on Python tooling (ruff via uv); adding a Node-based AST check means either bolting Node onto the lint job or creating a new job.
**Residual risk:** the AST guard remains paper architecture until someone writes it. The revision's own escape hatch — "If the AST check proves brittle in implementation: drop it" — is the most likely outcome. Sub-issue 4 is honestly framed as "do this, or document the drop," which is acceptable, but the parenthetical "Node-bundled-equivalent" misrepresents the dependency cost and should be removed.

### Charge 11 — Test stubbing / path-filtered integration

## NEW charges (revision-introduced)

### Charge 16: The "SessionStart cannot block the first prompt" claim is the revision's central load-bearing premise and it is undocumented

**The problem.** The revision's entire "bootstrap-in-flight defensive path" architecture rests on the assertion (line 71): "SessionStart hooks run in parallel and cannot block the first prompt. ... The user can submit a prompt immediately. The first `UserPromptSubmit` ... may race the bootstrap." This is a paraphrase fusion of two unrelated doc passages — "run in parallel" (intra-event, L441) and "Shows stderr to user only" on exit-2 (no decision-control blocking, L655) — into a claim about wall-clock concurrency between SessionStart and the user's first turn. **The docs do not say this.** The `additionalContext` delivery doc (L763) explicitly says SessionStart context arrives "at the start of the conversation, before the first prompt," which is the opposite implication.

**Why it matters.** If the harness *does* gate the first turn on SessionStart completion (most likely given the `additionalContext` timing contract), the user experiences a 30-90s freeze on first install with no progress indicator, the `!fs.existsSync(venvPython)` defensive path in `refresh-catalog-on-stale.js` is dead code, and the bootstrap-failure banner is delivered before the user has done anything (good — they see it). If the harness *does not* gate, the failure-banner is delivered into a conversation that may already have completed turns against a stale catalog. Either way, the design needs to be built against the actual behavior, not a doc-citation read.

**The question that must be answered.** Run a real `node` hook on `SessionStart` with a `sleep 10` and observe whether (a) the user can type into the prompt during that 10s, (b) the harness shows the prompt input as queued, or (c) the harness blocks input entirely. The answer must be empirical, not doc-derived. Until it is answered, every "race" / "in-flight" / "skip silently" sentence in the revision is unverified.

### Charge 17: PyYAML wheel matrix understates the platform-tag surface; the "fully offline" claim still has a hole

**The problem.** § Package distribution choice claims "Windows / macOS / Linux × cpython 3.11/3.12/3.13 = ~9 wheels" gives offline coverage. PyYAML on PyPI ships separate wheels for `manylinux_x86_64`, `manylinux_aarch64`, `musllinux_x86_64` (Alpine), `musllinux_aarch64`, `macosx_x86_64`, `macosx_arm64`, `win_amd64`, and `win_arm64` — for each of three Python versions. The real matrix is 24+ wheels, not 9. A consumer on Alpine Linux (a common Docker base image) installs the bundled `manylinux2014` wheel and gets `ERROR: ... is not a supported wheel on this platform`. With `--no-index`, there is no fallback.

**Why it matters.** "Fully offline" is the headline justification for the wheel-bundling pivot (charge 3 resolution). If it is not actually offline on Alpine or Linux ARM64, the bundling decision delivers cost (5.5+ MB to the plugin cache, release-tooling complexity) without the property it promised, and the consumer hits a worse failure than the v0.3.x bare-python class (silent install failure vs. clear "module not found").

**The question that must be answered.** What is the exhaustive platform-tag enumeration the release tooling will run? If the answer is "we don't support Alpine / ARM64 Linux," state that as an explicit non-support in the README and document the fallback (manual `--break-system-packages pip install pyyaml` from PyPI? source build via `--no-build-isolation` with hatchling pre-staged?). If the answer is "we support all of them," show the full `pip download` matrix loop in sub-issue 1, not the elided `# repeat for each (platform, python_version) pair` placeholder.

### Charge 18: The AST guard's "acorn (Node-bundled-equivalent)" parenthetical misrepresents a real dependency

**The problem.** § CI implications line 352: "AST-based using `acorn` (the parser Node bundles internally via `acorn` as a transitive dep of many tools, or installed as a dev dep)." Node does not expose `acorn` to user code; "many tools transitively depend on it" is not equivalent to "it is available to require." `package.json` at HEAD has no `acorn` dep and no `devDependencies` block at all. Adding it requires `npm install acorn --save-dev`, `package-lock.json` enters version control, the lint CI job grows an `npm ci` step, and Node 20's lockfile-v3 semantics become part of the build contract.

**Why it matters.** This is a small but real expansion of the project's dependency surface, dressed up as a freebie. Sub-issue 4's "or documented drop" escape hatch is fine, but readers should not be misled into thinking the AST check is dependency-free.

**The question that must be answered.** If acorn ships, what is the dev-dependency policy for hooks/ — does the plan accept `node_modules` in the plugin's distribution tree? Per plugins-reference.md L583 ("If your hook depends on Node packages, install them via a `SessionStart` hook into `${CLAUDE_PLUGIN_DATA}/node_modules`"), shipping `node_modules` in `${CLAUDE_PLUGIN_ROOT}` is supported but adds another bundled-artifact dimension. Or is acorn a *CI-only* dep, never present at consumer runtime? Probably the latter — but the plan does not say.

---

### Charge 19: The CI integration matrix omits macOS, which is the platform with the gnarliest wheel-resolution edge cases

**The problem.** § Test strategy integration matrix: `ubuntu-latest, windows-latest × Python 3.11, 3.12, 3.13`. macOS is omitted with no rationale. macOS has the most complex wheel-tag landscape (`x86_64` vs `arm64`, `macosx_11_0` vs `macosx_12_0` baselines, universal2), and is a primary developer platform for the user base.

**Why it matters.** charge 3 / charge 17 wheel-tag bugs will not be caught in CI for the platform most likely to hit them. The cost of adding `macos-latest` to the matrix is one YAML line.

**The question that must be answered.** Add macOS or state explicit non-support. The current silence is the worst of both worlds.

## Recommendation

**REVISE-AGAIN.** Two MAJOR charges (16 and 17) are new and load-bearing. Charge 16 in particular: the revision's central architectural premise — that bootstrap is non-blocking and the defensive path handles a real race — has been derived from a doc misreading and must be empirically verified before the rest of the design is committed to issues. Charge 17 means the "offline" property the bundling pivot delivers is partial at best; the revision needs to either commit to the full platform-tag matrix or scope down the claim. Neither requires a fundamental redesign — these are gaps in the spec, not flaws in the architecture — so a planner pass 3 with empirical verification of charge 16 and an exhaustive wheel-matrix or explicit-non-support for charge 17 should be enough to greenlight.

**Pass-1 charge most worth re-litigating:** Charge 2. The pass-1 question — "Does the SessionStart hook complete synchronously before the user's first prompt is accepted?" — was the right question. The revision answered it with a confident "no" derived from misreading "in parallel." The right answer is "run it and see," and that is the single empirical fact that locks or unlocks the rest of the design.
