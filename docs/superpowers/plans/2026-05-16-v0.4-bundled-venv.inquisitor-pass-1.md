# Inquisitor pass 1 — v0.4 plan

Reviewing `docs/superpowers/plans/2026-05-16-v0.4-bundled-venv.md` at HEAD.

## MAJOR (must resolve before pass 2)

### Charge 1: `hooks.json` registers `SessionStart` as a single array — the plan's "ordered before `check-catalog-health.js`" claim is unverified and the ordering mechanism is undocumented

**The problem.** § Proposed design opens with: "Add a new hook `hooks/bootstrap-venv.js` registered on `SessionStart`, ordered **before** `check-catalog-health.js`." But `hooks/hooks.json:3-12` registers `SessionStart` as a single matcher object containing a single-element `hooks` array. The plan does not specify how ordering is achieved (two entries in the same `hooks:` array? Two matcher objects? Same matcher group?), nor does it cite a doc claiming the harness guarantees in-array execution order at all. Anthropic's hooks doc shape is not quoted on this point in the References section.

**Why it matters.** If `check-catalog-health.js` runs *before* `bootstrap-venv.js` on a fresh install, it sees a missing catalog, but the venv it wants to use for refresh does not yet exist. The plan describes `refresh-catalog-on-stale.js` (UserPromptSubmit) handling the venv-missing case fail-open — fine — but it says nothing about `check-catalog-health.js` (SessionStart) and whether *it* needs the same defensive path. If the contract is "bootstrap runs first, then health check can assume venv exists," that contract has to be enforced by the registration shape, and the registration shape has to be documented as enforceable.

**The question that must be answered.** What is the exact `hooks.json` shape for the two SessionStart hooks, and what Anthropic doc citation guarantees that shape executes in the written order? If no such guarantee exists, both SessionStart hooks must independently handle the "venv missing" case and the plan needs to say so.

### Charge 2: SessionStart blocking semantics — the plan never states whether bootstrap blocks the session, but its own time estimate makes the answer load-bearing

**The problem.** The plan's CI section (§ CI implications) casually notes "~30-60s for venv + install." § Proposed design step 5 says "Always exit 0 (never block session start)" — but "never block" is doing two different jobs in that sentence. It could mean (a) the hook *process* always exits 0 so the harness doesn't fail-stop the session, or (b) the user's first prompt is not gated on bootstrap completion. The plan never disambiguates.

**Why it matters.** SessionStart hooks run synchronously before the user can submit a prompt (the harness spec is explicit about this — `additionalContext` from SessionStart needs to be in scope before the first turn). A 30-60s blocking startup on first install, with no progress indicator, will read to the consumer as "Claude Code hung." On a slow network where pip has to fetch hatchling + pyyaml wheels, the wait could be minutes. Yet the plan also relies on `additionalContext` from SessionStart to surface bootstrap-failure banners, which means the hook *must* run to completion before the session is usable — i.e., it *does* block.

**The question that must be answered.** Does the SessionStart hook complete synchronously before the user's first prompt is accepted? If yes, what does the user see during the 30-60s wait — and is there any timeout / progress mechanism? If no, what happens to UserPromptSubmit hooks that run while bootstrap is still in flight (`refresh-catalog-on-stale.js` would see `!fs.existsSync(venvPython)` and skip — fine — but is the user told why)?

### Charge 3: Build isolation will pull hatchling from the network on every fresh install — the "fully offline" claim is wrong

**The problem.** § Package distribution choice option (b) is recommended on the grounds that it "works fully offline (pip resolves `pyyaml` and `hatchling` from its own cache or falls back to PyPI only if not cached — and pyyaml is so ubiquitous it's almost always cached)." This is wishful thinking presented as a design property. `pyproject.toml:1-3` declares `requires = ["hatchling"]` with PEP 517 build isolation, which is pip's default. On a fresh consumer machine with no pip wheel cache (the common case — pip's cache is per-user and per-Python-version, and a brand-new bootstrap venv has *no* cache by definition), pip will fetch hatchling + its transitive deps (`pluggy`, `packaging`, `pathspec`, `trove-classifiers`, `editables`, etc.) from PyPI on every fresh bootstrap.

**Why it matters.** The plan repeatedly leans on offline-friendliness as a justification (§ Open questions risk 6, § Package distribution choice rationale bullet 2). It is not offline-friendly. A network-down first-install will fail. An IT-managed environment that proxies or blocks PyPI will fail. The plan's open question 6 ("`pyyaml` resolution offline") underestimates the dependency surface by an order of magnitude — it's not just pyyaml, it's the entire hatchling build-system graph.

**The question that must be answered.** Will v0.4 disable build isolation (`pip install --no-build-isolation`) and require the bootstrap interpreter to already have hatchling? Will it bundle the wheel (option a) after all? Will it accept the network dependency and update the risk language to match reality? Pick one — but the current claim "works fully offline" is not defensible.

### Charge 4: `pip install "${CLAUDE_PLUGIN_ROOT}"` with spaces in the path is not analyzed

**The problem.** § Hook invocation refactor shows the venv-Python path constructed with `path.join(process.env.CLAUDE_PLUGIN_DATA, ...)` and embedded in a command string with `"${venvPython}" -m claude_wayfinder catalog build`. The plan also proposes `pip install "${CLAUDE_PLUGIN_ROOT}"` for the bootstrap install step. On Windows, `${CLAUDE_PLUGIN_ROOT}` resolves under `~/.claude/plugins/cache/...`, and the user's home directory frequently contains spaces (`C:\Users\First Last\...`). The plan never addresses quoting through the bootstrap subprocess chain.

**Why it matters.** This is exactly the v0.3.2/v0.3.3 pattern repeating: a plan that ignores a foreseeable Windows-path failure and then has to ship a patch when a consumer reports it. The `parseCmd` regex in `hooks/refresh-catalog-on-stale.js:259-267` only handles `"quoted"` and `\S+` tokens — if the venv-Python path contains a space and the new bootstrap hook reuses this parser style, the command splits on the space inside the path. And `pip install <path>` interpretation depends on whether pip sees the path as one argument; if the path is passed unquoted through a shell, it fragments.

**The question that must be answered.** Walk through, with explicit shell-vs-no-shell semantics, what happens when `${CLAUDE_PLUGIN_ROOT}` is `C:\Users\First Last\.claude\plugins\cache\claude-wayfinder@0.4.0`. Show that every `spawnSync` call in the bootstrap pipeline passes the path correctly. The plan must show args-array invocation (`spawnSync(prog, [arg1, arg2], { shell: false })`) explicitly — not command-string parsing.

### Charge 5: The `${PY}` env-var override collides with a real, widespread convention

**The problem.** § Bootstrap interpreter source step 1 proposes `PY` as the environment-variable override. `PY` is the documented configuration variable for the Windows Python launcher itself (`py.ini` honors `PY_PYTHON`, and various third-party tooling uses `PY` for "the Python to use"). Using a bare `PY` name in an unscoped, machine-wide env-var space is a collision waiting to happen — a consumer who has `PY=python3.10` set for some other tool would silently route the bootstrap to a too-old interpreter.

**Why it matters.** The plan's own probe (`-c "import sys; sys.exit(0 if sys.version_info >= (3, 11) else 1)"`) would catch the version mismatch and fall through — but only if step 1 *falls through on probe failure*. § Bootstrap interpreter source step 1 says "if `${PY}` is set and points to a working Python ≥3.11, use it" but does not explicitly state the fallthrough behaviour when `${PY}` is set but fails the probe. Worse: the test seam `BOOTSTRAP_PYTHON_OVERRIDE` (§ Test strategy) is namespaced. The runtime override is not. That asymmetry is a tell.

**The question that must be answered.** Why is the runtime override `PY` and not `CLAUDE_WAYFINDER_PY` (or `BOOTSTRAP_PYTHON`)? What is the explicit fallthrough behaviour when `${PY}` is set but fails the version probe — fail loud (treat as user error) or silent fallthrough to next candidate?

### Charge 6: `built_for_project` is owned by `refresh-catalog-on-stale.js` but the bootstrap-venv hook ignores it — first session in a new project will silently use a stale catalog if the venv is fresh

**The problem.** `hooks/refresh-catalog-on-stale.js:224-231` reads `catalogJson.built_for_project` and forces a refresh on project mismatch. This is a UserPromptSubmit hook. The new SessionStart `bootstrap-venv.js` (§ Proposed design) only manages the venv lifecycle — it has no awareness of catalog state or project root. § Hook invocation refactor adds a "venv missing → skip silently" path to `refresh-catalog-on-stale.js`.

**Why it matters.** Consider: user installs v0.4 fresh in project A. SessionStart builds the venv (slow). UserPromptSubmit refreshes catalog for project A. User opens Claude Code in project B. SessionStart sees venv.version matches — no-op. UserPromptSubmit fires, sees `built_for_project` mismatch, attempts refresh — but the existing `parseCmd`-style path computation must now resolve the venv-Python path correctly even though the venv was materialized in a prior session, possibly under a now-different `${CLAUDE_PLUGIN_DATA}` if the consumer is across machines / sync tools. The plan does not analyze this cross-session, cross-project handoff.

**The question that must be answered.** What invariants does the bootstrap hook establish that downstream hooks rely on, and which of those invariants survive (a) cross-session, (b) cross-project, (c) cross-machine `${CLAUDE_PLUGIN_DATA}` sync (e.g. roaming profile, OneDrive)? Each one needs a stated answer or an explicit non-support note.

## MODERATE (should resolve before greenlight)

### Charge 7: The `hooks/_python/VERSION` file is a parallel version-of-truth that breaks under squash-merge release flows

**The problem.** § Sub-issues 1 and 5 establish that `hooks/_python/VERSION`, `pyproject.toml [project] version`, and `.claude-plugin/plugin.json version` all must be kept in lockstep, manually, per release. Sub-issue 1 says "could be automated with a pre-tag hook or a `scripts/bump-version.py` helper; out of scope for the sub-issue itself."

**Why it matters.** Three files, one truth. The first release that ships with two of three bumped and one stale will write a `venv.version` sentinel that disagrees with the actual installed package version, causing either (a) the venv claims to be up-to-date when the source is older, masking install bugs, or (b) eternal rebuilds because the sentinel never matches. "Out of scope" is how this becomes a v0.4.1 patch. § Package distribution choice already explains why option (b) was picked — but option (b) has `pyproject.toml` as the *actual* source of truth pip reads. There is no architectural reason for a separate `VERSION` file; the plan justifies it as "parsing TOML in Node without deps is ugly." Node 22 ships a built-in TOML parser; even on Node 20, a 20-line regex for `^version = "(.*)"` under `[project]` is not ugly enough to justify a third truth-source.

**The question that must be answered.** Why not read `pyproject.toml` directly (regex or built-in parser), eliminating the lockstep problem? If a separate file is genuinely required, what mechanism *prevents* — not just discourages — a release shipping with mismatched versions?

### Charge 8: The "lint guard" `test-no-bare-python-invocation` is test theater

**The problem.** § CI implications proposes a lint check that greps `hooks/*.js` for `"python "` / `"python3 "` strings. § Sub-issue 4 lists it as a deliverable.

**Why it matters.** This catches only the literal string. It does not catch `const cmd = "py" + "thon"`, does not catch `spawnSync("python", ...)` with the program name as a bare string (no trailing space), does not catch `spawnSync(process.env.SHELL || "python", ...)`, does not catch a hook that shells out to Python via `bash -c "python ..."`. It is the security-theater version of the actual invariant ("no hook shall spawn a Python interpreter outside of the venv-path resolver"). The plan presents it as a defense against regression of the v0.3.x failure shape — but the v0.3.x bugs would not have been caught by this grep either (the v0.3.2 bug spawned `claude-wayfinder`, not `python`; the v0.3.3 bug spawned `python` *with a trailing space* and would have been caught — but only by accident of formatting).

**The question that must be answered.** What does the lint check actually guarantee? If the goal is "no hook spawns a Python interpreter outside the venv-path resolver," express that as an AST-level check or a `spawnSync` argument inspection — not a substring grep. Otherwise drop it; lint that doesn't catch the real failure mode is worse than nothing because it produces false confidence.

### Charge 9: Failure-mode discipline elides the "interpreter found, venv created, pip install crashed mid-run" partial-state case

**The problem.** § Failure-mode discipline enumerates three failure surfaces: no interpreter, bootstrap failure, post-bootstrap corruption. § Proposed design step 3 says "On failure, delete `venv.version` so the next session retries." But what about the `${CLAUDE_PLUGIN_DATA}/venv/` directory itself? If `python -m venv` succeeds and `pip install` crashes (network drop, disk full mid-write, user Ctrl-C the parent process), the venv directory exists but is half-populated. The plan deletes `venv.version` (correctly) so next session retries, but does not delete `venv/`. § Proposed design existence-detection table row "Update with version bump" says "delete `venv/` then bootstrap" — fine for that case — but the table's "Corrupted (partial bootstrap)" row says "rebuild" without specifying whether the half-built venv is torn down first.

**Why it matters.** `python -m venv <dir>` against an existing non-empty directory has version-specific behaviour (some versions clobber, some refuse, some error). pip install against a half-built venv may succeed partially and produce silently broken imports. The post-failure cleanup discipline is the difference between "next session retries cleanly" and "permanently wedged install requiring manual `rm -rf`."

**The question that must be answered.** What is the exact cleanup sequence when bootstrap fails after `venv` creation but before `pip install` completes? Specify the rmdir, the order, and the failure-of-cleanup fallback.

### Charge 10: The release strategy assumes alpha tags work in the marketplace install path, but cites no evidence

**The problem.** § Release shape proposes `v0.4.0-alpha.1 → … → v0.4.0`. The plan does not cite any Anthropic doc confirming that `marketplace.json` accepts pre-release version tags, that `/plugin install` / `/plugin update` honors them, or that the cache directory naming (`~/.claude/plugins/cache/claude-wayfinder@v0.4.0-alpha.1`?) handles `@` and `.` in version strings. § References Anthropic plugin docs § Version management is cited generally but no specific quote on pre-release semantics.

**Why it matters.** This is a CLAUDE.md `# Cite Sources` violation in spirit — a load-bearing release-process decision with no verifiable source. If alpha tags are not supported, the plan's entire "release alphas, gather field feedback before final" strategy collapses to "release v0.4.0 to everyone, hope for the best."

**The question that must be answered.** Cite the doc that confirms pre-release version tags are accepted by the marketplace and the install/update flow. If no such citation exists, either verify empirically (and add the citation), or drop the alpha strategy in favor of a small-pool manual install via local clone.

### Charge 11: Test strategy stubs the entire bootstrap pipeline — there is no test that actually exercises a real `python -m venv` + `pip install`

**The problem.** § Test strategy unit-level says "Tests set [`BOOTSTRAP_PYTHON_OVERRIDE`] to `node` and verify the hook spawns it." The integration-level job is "opt-in" and runs only on PRs touching specific paths.

**Why it matters.** Every test in the unit suite verifies that the hook *would have called* `python -m venv` with the right args. None verify that the resulting venv actually has `claude_wayfinder` importable. The integration job is the only thing that does — and it's path-filtered, so a PR that, say, bumps `pyproject.toml` dependencies but doesn't touch `hooks/bootstrap-venv.js` or `hooks/refresh-catalog-on-stale.js` will not run it. This is exactly how v0.3.3 shipped: tests passed, the actual subprocess behaviour was different. The mock seam reproduces the test theater that allowed the v0.3.x regressions.

**The question that must be answered.** Why is the integration job path-filtered? Why not run it on every PR? At minimum, why not run it on every release tag? "It's slow" (~30-60s) is not an answer at the scale of a CI matrix that already runs lint + py311 + py312 + node + manifest in parallel.

## MINOR (note for record; resolve at author's discretion)

### Charge 12: § Open questions risk 5 dismisses the bundled `src/` size impact without measurement

The plan says "the source tree is small (kilobytes)" but does not include a number. `git ls-files src/ | xargs wc -c` would settle it in one command. If it is genuinely kilobytes, write the number; if it is megabytes, the marketplace cache implications (7-day retention of orphan versions) compound. Either way, replace the hedge with a measurement.

### Charge 13: The `built_for_project` field name and the new `venv.version` sentinel use inconsistent naming conventions

`built_for_project` is snake_case inside JSON; `venv.version` is a flat text file. Fine in isolation, but the plan does not establish whether the version sentinel should be JSON-shaped to match (`{"version": "0.4.0", "built_at": "..."}`) for future extensibility (debug info, last-rebuild timestamp). A bare text file forecloses on that without justification.

### Charge 14: § Hook invocation refactor proposes a shared helper `hooks/lib/venv-path.js` but `hooks/lib/` does not yet exist

Not a blocker, just unverified. `hooks/refresh-catalog-on-stale.js` lives at `hooks/` top level; no `lib/` subdirectory is referenced in `hooks/hooks.json` paths. Creating it is fine; the plan should explicitly name it as new structure rather than implying it.

### Charge 15: `unverified:` flagged items 1, 2, 3, 7 are all load-bearing but none are blocking-flagged

The plan author lists four `unverified:` items in passing prose, scattered across § Bootstrap interpreter source, § Test strategy, § CI implications, and § Open questions. Each could materially change the design if proven false. The plan should pull these into a single "must verify before sub-issue 2 starts" checklist, not bury them inline.

## What the plan does well

- The `${CLAUDE_PLUGIN_ROOT}` vs `${CLAUDE_PLUGIN_DATA}` distinction is correctly stated and the citations are real.
- The discriminator-table approach to "what state are we in" is structurally sound (charges 6 and 9 notwithstanding).
- § Update-time invalidation correctly identifies that `${CLAUDE_PLUGIN_DATA}` survives plugin updates and reasons about the mid-session-update edge case.
- The decision to make `BOOTSTRAP_*` env vars test seams is consistent with the existing `DISPATCH_GENERATOR_CMD` pattern.
- The plan does cite Anthropic docs with retrieval dates per § Cite Sources.
