## Distribution model (locked)

**v0.1 ships as Pattern A: documented Python prereq, no bundled runtime.** The user installs Python ≥3.11 themselves, then `pip install` (or `git clone` + `uv pip install -e .`) the package. This matches the precedent set by every runtime-bearing plugin in the Claude Code marketplace today.

**Why this shape (locked 2026-05-13):** The plugin-distribution research spike (#5, closed) established two facts that bound v0.1's distribution surface:

1. **Anthropic does not expose Claude Code's bundled Bun/Node runtime to skill subprocesses.** See [`anthropics/claude-code#30465`](https://github.com/anthropics/claude-code/issues/30465) (closed `not_planned`) and the spike write-up at `docs/exploration/2026-05-13-plugin-distribution.md`. A plugin cannot reuse the host's interpreter.
2. **No marketplace plugin bundles a runtime today.** Every runtime-bearing plugin we surveyed — `microsoft-docs` (Node 22+), `superpowers` (Node 18+), and the others enumerated in the spike doc — uses **Pattern A**: require the user to install the interpreter, document it in the README's install section.

**Implications:**

- README install instructions must lead with the Python prereq, in the same shape `microsoft-docs` documents Node ≥22.
- "Marketplace install → works without secondary install" is **not** a v0.1 goal. Deferred to v0.2 via spike #6 (`bin/`-based bundled-runtime experiment).
- Phrasing must match reality: "Install Python ≥3.11, then `pip install` (or `git clone + uv pip install -e .`), then use." No promise of zero-friction install.
- The `unverified:` tags in v1 around plugin-shape claims are now resolved — cite `docs/exploration/2026-05-13-plugin-distribution.md` and `anthropics/claude-code#30465` rather than carrying speculation.

**Citation:** `docs/exploration/2026-05-13-plugin-distribution.md` (spike write-up, committed in this branch), [`anthropics/claude-code#30465`](https://github.com/anthropics/claude-code/issues/30465) (upstream confirmation that the host runtime is not reusable), issue #5 (closed; spike), issue #6 (v0.2 bundled-runtime follow-up).

### Decision 1: Public API surface

**Answer (decision locked 2026-05-13):** v0.1 publishes a narrow API: `match.match`, `match.load_catalog`, `match.build_features`, `match.score`, `match.decide`, plus the dataclasses (`CatalogEntry`, `Features`, `ScoredEntry`, `Keyword`, `Triggers`) and the `VALID_DECISIONS` constant. `build_catalog.build_catalog` (the top-level entry) is published as part of the API. `health.py` becomes `_health.py` — internal, may change. **`match_filters.is_agent_routable` is internal** for v0.1 — keeps the stable API surface smaller; can be promoted in v0.2 if a caller surfaces a concrete need to reproduce the predicate semantics.

**Why this shape:** The 7-decision contract is the headline value (`README.md:L13-L14`), and the kernel functions (`score`, `decide`, `build_features`) are what consumers must call to integrate. Health metrics are tied to the harness telemetry pipeline (`health.py:L11-L13` references `~/.claude/state/router-drift.jsonl` and `dispatch-log.jsonl` — paths that mean nothing to an external user). Making health internal frees us to redesign it once we have a public consumer with an actual metrics need.

**Citation:** `src/claude_wayfinder/match.py:L44-L54` (decision enum), `match.py:L508-L562` (`score`), `match.py:L647-L761` (`decide`), `health.py:L1-L18` (harness-coupled module docstring).

**Issue to file (#2 in follow-up list):** "Define and document v0.1 public API: `__init__.py` exports + `docs/api.md`" — scope: rewrite `src/claude_wayfinder/__init__.py` to re-export the named symbols above, rename `health.py` → `_health.py`, keep `match_filters.is_agent_routable` un-exported (internal), update any test imports, add a one-page `docs/api.md` enumerating what is stable.

### Decision 2: Default-path policy

**Answer (decision locked 2026-05-13):** **Hard remove `~/.claude/...` defaults for v0.1 — no deprecation window.** The matcher, catalog generator, and CLI demo require explicit catalog and log paths — via argument, env var, or CLI flag. The env-var override path stays (`DISPATCH_CATALOG_PATH`, `DISPATCH_LOG_PATH`) for harness wiring, but the *fallback to `~/.claude/state/...` is removed entirely*. Missing path → clear error: `"--catalog PATH is required; no default in v0.1"`. Pre-1.0 is the right time to take this break — a public package should never point at a path it doesn't own.

**Why this shape:** `match.py:L223-L241` and `match.py:L244-L257` currently default to the harness layout. For a public package, defaulting state into a user's home directory under a path they may have never created is surprising and (per `health.py:L364`, `health.py:L722`) breaks CI runners that have no `~/.claude/state/`. Requiring explicit paths is small extra friction for the harness operator (they already export env vars) and removes a sharp edge for everyone else.

**Citation:** `src/claude_wayfinder/match.py:L223-L257`, `src/claude_wayfinder/health.py:L116`, `src/claude_wayfinder/health.py:L364-L365` (CI runners lack default path), `src/claude_wayfinder/build_catalog.py:L1892`.

**Issue to file:** "Remove `~/.claude/...` default fallbacks; require explicit catalog/log paths" — scope: edit `_resolve_catalog_path` / `_resolve_log_path` in `match.py`, the catalog default in `health.py`, and the home-derived path in `build_catalog.py`; add CLI flags to `cli.py`; update tests that relied on `Path.home()` defaulting.

### Decision 3: CLI demo

**Answer (decision locked 2026-05-13):** Ship `python -m claude_wayfinder demo`. It:

1. Loads a bundled demo catalog from `src/claude_wayfinder/fixtures/demo-catalog.json` (3-5 entries — `code-writer`, `python` skill, `papyrus-skyrim` skill, `gh-create-issue` skill — chosen because they exercise different scoring paths: agent + skill + path-glob + keyword).
2. Iterates a bundled list of example task descriptions from `src/claude_wayfinder/fixtures/demo-prompts.json` that **exercise all four decision branches** — `delegate`, `self_handle`, `ambiguous`, and `needs_more_detail`. The 7-decision contract is the elevator pitch; the demo must show it. A longer/louder demo is the acceptable cost.
3. For each prompt, prints: the input JSON, the matcher's output decision, and a one-line "this exercised X decision branch" annotation.
4. Exits 0 on success. Exits non-zero only on internal failures (bundled catalog corrupted, etc.) — no Claude Code install, no network, no user state required.

**Why this shape:** `README.md:L22-L30` already advertises this exact command. The README pitch ("No Claude Code install needed to evaluate the matcher") only holds if the demo is self-contained. Bundling the catalog and prompts inside the package means `pip install claude-wayfinder && python -m claude_wayfinder demo` works on a clean machine.

**Citation:** `README.md:L22-L30` (the promise), `src/claude_wayfinder/__init__.py:L1-L8` (no CLI exists today), `pyproject.toml:L29-L31` (commented-out entry).

### Decision 6: Skipped-test disposition

**Answer:** Three categories, three different treatments:

1. **Harness-invariant tests** (`test_build_catalog.py:L2860-L2917` — "code-writer must not list `mcp__github__add_issue_comment`", "code-reviewer must retain `mcp__github__create_pull_request_review`"): **delete**. These test the *user's harness config*, not the matcher. They're tracking GitHub read/write split policy from the harness, which has nothing to do with `claude-wayfinder` semantics.
2. **Live-catalog cascade** (`test_match.py:L1216-L1802` — ~13 tests that run the catalog generator against `~/.claude/agents/` then assert matcher behavior): **rewrite to use synthetic fixtures** (decision locked 2026-05-13 — accepted as the largest single chunk of v0.1 work). The fixtures already exist in `tests/fixtures/` (`tests/fixtures/skills/csv-utils/SKILL.md`, `tests/fixtures/agents/code-writer.md`, etc.) and serve as scaffolding. The test bodies need to point `--agents-dir` and `--skills-dir` at `tests/fixtures/agents/` and `tests/fixtures/skills/` instead of `REPO_ROOT / "agents"`. The *behavior under test* (matcher returns correct decision for a generated catalog) is valuable and should not be lost.
3. **Genuine "skip on missing optional input"** (e.g. `test_build_catalog.py:L404`, `test_build_catalog.py:L3160-L3212` — skip when corpus/sidecars absent): **leave as-is**. These are testing the generator's graceful-degradation path, and skip is the correct semantics.

**Why this shape:** A skipped test is invisible work — CI passes, but coverage is hollow. Deleting category 1 removes confusion (these tests do not belong here). Rewriting category 2 restores ~13 real test cases worth of coverage on the matcher's decision branches. Category 3 needs no change.

**Citation:** `tests/test_match.py:L1237-L1240`, `tests/test_build_catalog.py:L2873-L2874`, `tests/test_build_catalog.py:L2906-L2907` (the 3 explicit `pytest.skip` sites — confirmed by `Grep "pytest\.skip"` over `tests/`), `tests/test_match.py:L1216-L1217` (the `_AGENTS_DIR = REPO_ROOT / "agents"` definition that drives the cascade), `tests/fixtures/agents/code-writer.md` + `tests/fixtures/skills/csv-utils/SKILL.md` (existing synthetic fixtures usable for the rewrite).

**Note:** The user's brief stated "13 tests skip." `Grep "pytest\.skip"` shows 3 explicit skip statements, but the live-catalog helper is called by ~13 test bodies — so the user's count is the *cascade impact*, not the literal skip-statement count. Both views are consistent.

**Issue to file:** "Disposition skipped tests: delete harness-invariant, rewrite live-catalog cascade against synthetic fixtures, keep optional-input skips" — scope: delete `test_subagent_github_write_tools_removed` and `test_review_agents_retain_create_pull_request_review`; rewrite `_build_live_catalog` to take `agents_dir` + `skills_dir` arguments pointing at the synthetic fixture tree; run `pytest -v` and confirm zero unexpected skips remain.

### Decision 8: Versioning + release

**Answer:** Adopt **SemVer with explicit pre-1.0 caveat**. v0.1.0 means "first publicly evaluable cut; API may change between 0.x.y releases; we will not make breaking changes within an 0.x line without a 0.(x+1) bump." Release flow for v0.1.0:

1. Land all v0.1 milestone issues on `main` via PR.
2. Bump `pyproject.toml:L7` from `version = "0.0.1"` to `version = "0.1.0"`.
3. Write `CHANGELOG.md` (Keep-a-Changelog format) for the v0.1.0 entry — list the public-API surface, default-path policy change, demo command, CI workflow.
4. Tag `v0.1.0` on `main` (`git tag -a v0.1.0 -m "..."`, `git push origin v0.1.0`).
5. Create a GitHub Release from the tag, paste the CHANGELOG entry, attach the wheel + sdist built by the CI `build` job.
