# claude-wayfinder v0.1.0 Cut-Line Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to execute the issues filed from this plan. Steps in the per-issue scope sections use checkbox (`- [ ]`) syntax.

**Goal:** Lock the decisions that define `claude-wayfinder` v0.1.0 — the first public release — so the port branch (PR #3) can be reviewed and merged on a clear, narrow contract.

**Architecture:** v0.1 ships as a **sideloadable Claude Code plugin** consumed via `/plugin marketplace add glitchwerks/claude-wayfinder` (the repo carries both `.claude-plugin/marketplace.json` and `.claude-plugin/plugin.json`). The plugin exposes one demonstration skill (`skills/dispatch/SKILL.md`) that exercises the matcher against bundled fixtures. The underlying Python package (`src/claude_wayfinder/`) — the deterministic 7-decision matcher (`match.py`), the catalog generator (`build_catalog.py`), the shared routability predicate (`match_filters.py`) — remains the engine; a contributor CLI demo (`python -m claude_wayfinder demo`) ships alongside for evaluating the algorithm without installing Claude Code. The health-reporting module is in scope as a *non-public, internal* module. Hooks, agents, and harness plumbing stay in the private harness.

**Tech Stack:** Python ≥ 3.11 (per `pyproject.toml:L12`), stdlib only at runtime (catalog generator depends on `pyyaml ≥ 6.0` per `pyproject.toml:L20`), `pytest` + `ruff` for dev, GitHub Actions for CI, Hatchling build backend, Claude Code plugin manifest schema per [Plugins reference](https://code.claude.com/docs/en/plugins-reference) (fetched 2026-05-13).

**Tracking:** issue #4 (this plan), milestone `v0.1.0`, port PR #3 (closes #2).

## Distribution model (locked — revised 2026-05-13 pass 2)

**v0.1 ships as a sideloadable Claude Code plugin.** Primary user path is two slash commands inside Claude Code:

```text
/plugin marketplace add glitchwerks/claude-wayfinder
/plugin install claude-wayfinder@claude-wayfinder
```

**unverified: the second-line syntax `<plugin-name>@<marketplace-name>` where marketplace name == plugin name has no public precedent.** The only worked Anthropic example uses distinct names (`superpowers@claude-plugins-official`). Two-step install pattern itself is cited per [Discover and install prebuilt plugins](https://code.claude.com/docs/en/discover-plugins) (fetched 2026-05-13) — the only documented "install from GitHub" path is via marketplace add + plugin install; there is **no** `/plugin install owner/repo` shortcut for non-marketplace repos. **Resolution:** the implementer of Step 7 (manifests + skill) must perform a live `/plugin install` against the published marketplace as part of that issue's acceptance criteria; if self-naming fails, fall back to distinct names (`glitchwerks-wayfinder` as marketplace name, `claude-wayfinder` as plugin) and update the README in the same PR. See § Open Questions.

The repo carries both manifest files at root:

- **`.claude-plugin/marketplace.json`** — required schema per [Create and distribute a plugin marketplace](https://code.claude.com/docs/en/plugin-marketplaces) (fetched 2026-05-13). Fields: `name` (kebab-case, public-facing), `owner` (`{name, email?}`), `plugins` (array with at least one entry pointing at `./` for the same-repo plugin).
- **`.claude-plugin/plugin.json`** — required-field-only minimum is just `name`. v0.1 populates `name`, `version` (pinned, matching `pyproject.toml` version per [Plugins reference § Version management](https://code.claude.com/docs/en/plugins-reference) fetched 2026-05-13), `description`, `author`, `homepage`, `repository`, `license`, `keywords`.

**The plugin's user-visible surface is a single demonstration skill: `skills/dispatch/SKILL.md`.** That skill loads the bundled demo catalog, runs the matcher across the bundled demo prompts, and returns the seven-decision output. The skill confirms the plugin *works after install* — not just that the manifest validates. **v0.1's plugin is an evaluation surface, not a daily-driver router** (per pass-2 non-blocking charge 12): a user installing v0.1 can see the matcher decide against bundled fixtures, but cannot point it at their own agents/skills until the configurable-catalog work in Decision 9 (v0.2) lands.

**Pattern A precedent:** This shape — repo is itself a marketplace listing one plugin — matches the precedent set by `superpowers` and `microsoft-docs` (both ship via marketplace add, both expose user-facing skills, neither ships as a PyPI wheel). The user is a Claude Code user evaluating dispatch behavior; meeting them inside Claude Code is the cleanest path.

**Contributor path** (separate, secondary):

```bash
# For contributors who want to hack on the matcher without Claude Code
git clone https://github.com/glitchwerks/claude-wayfinder.git
cd claude-wayfinder
uv pip install -e ".[dev]"
python -m claude_wayfinder demo
```

**Wheel / sdist / PyPI ceremony is dropped from v0.1.** The "release" is a git tag + a GitHub Release page carrying the changelog. There are no attached binaries because no consumer needs them: plugin users sideload from the git ref, contributors clone the repo. PyPI is deferred until a consumer with a real need surfaces — not "v0.2", just **deferred until justified** (this is the principled framing per inquisitor charge 8 and the user-locked decision; see § 3 Decision 8).

**Why this shape (locked 2026-05-13):** The plugin-distribution research spike (#5, closed) established two facts that bound v0.1's distribution surface, and one consequence:

1. **Anthropic does not expose Claude Code's bundled Bun/Node runtime to skill subprocesses.** See [`anthropics/claude-code#30465`](https://github.com/anthropics/claude-code/issues/30465) (closed `not_planned`) and the spike write-up at `docs/exploration/2026-05-13-plugin-distribution.md`. A plugin cannot reuse the host's interpreter.
2. **No marketplace plugin bundles a runtime today.** Every runtime-bearing plugin we surveyed — `microsoft-docs` (Node 22+), `superpowers` (Node 18+), and the others enumerated in the spike doc — requires the user to install the interpreter and document it in the README.
3. **Consequence (per inquisitor charge 5):** v0.1 does **not** meet the originally-stated "marketplace install → works without secondary install" bar. That bar is structurally unreachable today per #30465 and is the entire purpose of v0.2 spike #6. The plugin sideload path still requires Python ≥3.11 on `$PATH` before the demonstration skill can call the matcher. This gap is named, not finessed.

**Citation:** `docs/exploration/2026-05-13-plugin-distribution.md` (spike write-up, committed in this branch), [`anthropics/claude-code#30465`](https://github.com/anthropics/claude-code/issues/30465), issue #5 (closed; spike), issue #6 (v0.2 bundled-runtime follow-up), [Plugins reference](https://code.claude.com/docs/en/plugins-reference) (fetched 2026-05-13), [Discover and install prebuilt plugins](https://code.claude.com/docs/en/discover-plugins) (fetched 2026-05-13), [Create and distribute a plugin marketplace](https://code.claude.com/docs/en/plugin-marketplaces) (fetched 2026-05-13).

## 3. The Nine Decisions

Each decision below is a single line answer + cited rationale + scope of the follow-up issue the user should file after locking the plan.

### Decision 1: Public API surface

**Answer (decision locked 2026-05-13):** v0.1 publishes a narrow API: `match.match`, `match.load_catalog`, `match.build_features`, `match.score`, `match.decide`, plus the dataclasses (`CatalogEntry`, `Features`, `ScoredEntry`, `Keyword`, `Triggers`) and the `VALID_DECISIONS` constant. `build_catalog.build_catalog` (the top-level entry) is published as part of the API. `health.py` becomes `_health.py` — internal, may change. **`match_filters.is_agent_routable` is internal** for v0.1.

**Why this shape:** The 7-decision contract is the headline value (`README.md:L14`), and the kernel functions (`score`, `decide`, `build_features`) are what consumers must call to integrate. Health metrics are tied to the harness telemetry pipeline (`health.py:L11-L13` references `~/.claude/state/router-drift.jsonl` and `dispatch-log.jsonl` — paths that mean nothing to an external user). Making health internal frees us to redesign it once we have a public consumer with an actual metrics need.

**Citation:** `src/claude_wayfinder/match.py:L44-L54` (decision enum), `match.py:L508-L562` (`score`), `match.py:L647-L761` (`decide`), `health.py:L1-L18` (harness-coupled module docstring).

**Issue to file:** "Define and document v0.1 public API: `__init__.py` exports + `docs/api.md`" — scope: rewrite `src/claude_wayfinder/__init__.py` to re-export the named symbols above, rename `health.py` → `_health.py`, keep `match_filters.is_agent_routable` un-exported (internal), update any test imports, add a one-page `docs/api.md` enumerating what is stable.

### Decision 2: Default-path policy

**Answer (decision locked 2026-05-13; expanded for inquisitor charge 3):** **Hard remove the `Path.home() / ".claude" / ...` fallback for v0.1 — no deprecation window.** This affects three resolution paths in `match.py` and the hard-coded `Path.home()` references in `health.py` and `build_catalog.py`. | Code site | Current resolution | v0.1 resolution |
| --- | --- | --- |
| `match.py:L235-L237` (catalog: env var) | `DISPATCH_CATALOG_PATH` env var | **Keep** — explicit override |
| `match.py:L238-L240` (catalog: `CLAUDE_HOME`) | `$CLAUDE_HOME/state/dispatch-catalog.json` | **Remove** — this also defaults into a path the public package does not own. Harness operators already set `DISPATCH_CATALOG_PATH` directly; the `CLAUDE_HOME` middle step is a convenience for the private harness, not a contract. |
| `match.py:L241` (catalog: home fallback) | `~/.claude/state/dispatch-catalog.json` | **Remove** — error: `"--catalog PATH is required; no default in v0.1"` |
| `match.py:L254-L256` (log: env var) | `DISPATCH_LOG_PATH` env var | **Keep** — explicit override |
| `match.py:L257` (log: home fallback) | `~/.claude/state/dispatch-log.jsonl` | **Remove** — same error pattern |
| `health.py:L116`, `health.py:L1100-L1101`, `health.py:L1141` | Hard-coded `Path.home() / ".claude" / ...` | **Remove** — `_health.py` becomes internal per Decision 1; callers must pass paths explicitly |
| `build_catalog.py:L1892` | `Path.home() / ".claude"` | **Remove** — explicit `--state-dir` argument |

Missing path → clear error: `"--catalog PATH is required; no default in v0.1"` (or the equivalent for log / state dir). Pre-1.0 is the right time to take this break — a public package should never point at a path it doesn't own.

**Env-var overrides retained for v0.1:** `DISPATCH_CATALOG_PATH`, `DISPATCH_LOG_PATH`. The `CLAUDE_HOME` env var is **dropped** — its only purpose is to compose a default path the public package does not own.

**Why this shape:** For a public package, defaulting state into a user's home directory under a path they may have never created is surprising and (per `health.py:L364`, `health.py:L722`) breaks CI runners that have no `~/.claude/state/`. Requiring explicit paths is small extra friction for the harness operator (they already export env vars) and removes a sharp edge for everyone else. The `CLAUDE_HOME` middle step (charge 3) is named explicitly so the implementer cannot silently leave it behind.

**Citation:** `src/claude_wayfinder/match.py:L223-L257` (full three-step resolution verified 2026-05-13), `src/claude_wayfinder/health.py:L116`, `src/claude_wayfinder/health.py:L364-L365` (CI runners lack default path), `src/claude_wayfinder/build_catalog.py:L1892`.

**Issue to file:** "Remove `~/.claude/...` default fallbacks and `CLAUDE_HOME` middle step; require explicit catalog/log paths" — scope: edit `_resolve_catalog_path` / `_resolve_log_path` in `match.py` per the table above, the hard-coded paths in `health.py` and `build_catalog.py`, add CLI flags to `cli.py`, update tests that relied on `Path.home()` defaulting.

### Decision 3: CLI demo and demonstration skill

**Answer (decision locked 2026-05-13; expanded for inquisitor charge 13 and the distribution-shape pivot):** Ship two artifacts that exercise the matcher:

1. **`skills/dispatch/SKILL.md`** — the user-facing plugin skill. Calls into the bundled matcher with the bundled demo catalog + prompts, returns one of the seven decisions with the decision branch labelled. This is the artifact a plugin user invokes after `/plugin install`.
2. **`python -m claude_wayfinder demo`** — the contributor CLI. Same underlying engine; different surface. Iterates the bundled prompts and prints input/output JSON to stdout.

Both exercise **all 7 decision branches** (inquisitor charge 13, user-locked) — `delegate`, `self_handle`, `self_handle_unaided`, `advisory`, `ambiguous`, `ask_user`, `needs_more_detail`. The README pitch (`README.md:L14`) is the *seven-decision* enum; the demo and skill must show all seven, not a 4-of-7 subset. The cost is one additional prompt + expected-output line per missing branch — marginal.

Demo / skill workflow:

1. Load a bundled demo catalog from `src/claude_wayfinder/fixtures/demo-catalog.json` (3-5 entries — `code-writer`, `python` skill, `papyrus-skyrim` skill, `gh-create-issue` skill — chosen because they exercise different scoring paths: agent + skill + path-glob + keyword).
2. Iterate bundled example task descriptions from `src/claude_wayfinder/fixtures/demo-prompts.json`. **7 prompts, one per decision branch.**
3. For each prompt, print: the input JSON, the matcher's output decision, and a one-line "this exercised X decision branch" annotation.
4. Exit 0 on success. Non-zero only on internal failures (bundled catalog corrupted, etc.) — no Claude Code install, no network, no user state required for the CLI demo. The skill runs inside Claude Code by definition.

**Why this shape:** `README.md:L14` advertises seven decisions; the demo and the skill must honour that pitch end-to-end. Bundling the catalog and prompts inside the package means the contributor path (`pip install -e .` + `python -m claude_wayfinder demo`) works on a clean machine, and the skill (`skills/dispatch/SKILL.md`) works after the plugin is sideloaded into Claude Code. Two surfaces, one engine, one fixture set.

**Citation:** `README.md:L14` (the seven-decision pitch), `src/claude_wayfinder/__init__.py:L1-L8` (no CLI exists today), `pyproject.toml:L29-L31` (commented-out entry), [Plugins reference § Skills](https://code.claude.com/docs/en/plugins-reference) (fetched 2026-05-13) for the skill layout.

**Issue to file:** "Implement `python -m claude_wayfinder demo` + `skills/dispatch/SKILL.md` with bundled fixtures covering all 7 decision branches" — scope: create `cli.py`, `__main__.py`, `fixtures/demo-catalog.json`, `fixtures/demo-prompts.json`, `skills/dispatch/SKILL.md`; uncomment + activate the `[project.scripts]` block in `pyproject.toml`; add `tests/test_cli_demo.py` that runs the demo via `subprocess.run([sys.executable, "-m", "claude_wayfinder", "demo"])` and asserts the expected decisions appear in stdout (one assertion per branch). **No separate `test_skill_dispatch.py`** (pass-2 charge 5): the skill body is markdown that invokes the same Python entry point the CLI demo exercises — a second test file would duplicate `test_cli_demo.py` under a misleading name. If integration-test coverage of the skill harness becomes load-bearing, it is a v0.2 concern and requires a Claude Code harness fixture that does not exist in v0.1 scope.
